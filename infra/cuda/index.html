CUDA 推理算子开发
从 0 到 1 动手实践教程

面向 AI 推理开发者：从向量加法起步，经过访存优化、Tensor Core GEMM、异步拷贝流水线，一路做到 FlashAttention、Paged Decode Attention、量化 GEMM、MoE 和 CUDA Graph，最后把自己写的算子接入一个可运行的小型 LLM 推理引擎。

全程围绕一个持续演进的仓库 infer-kernels。每个阶段都包含：学习目标、需实现的功能、实践要点、验证方式、阶段性产出。

15 + 1个阶段 + 结业项目
4代架构：Ampere → Hopper → Blackwell → Blackwell Ultra
≈ 11–13 周参考总用时（每周 5 个工作日）
A100 即可完成阶段 0–7、9–14；阶段 8 需 H100 / B200 / B300

i. 如何使用本教程

推理算子开发的核心能力是三件事：知道瓶颈在哪（访存、计算还是调度开销）、知道硬件能提供什么（Tensor Core、异步拷贝、CUDA Graph 等），以及能用数据证明优化有效（正确性测试加性能基准）。每个阶段都按下面的结构组织：

模块作用怎么用
🎯 学习目标本阶段要弄懂的硬件机制与优化原理先读参考资料，能画出数据流图、说清瓶颈后再动手
🛠 需实现的功能本阶段要往 infer-kernels 里加的 kernel、测试和基准按列出的版本逐个实现，每个版本都保留，便于对比
💡 实践要点关键设计约束、易错点和调优技巧当作代码审查清单，提交前逐条对照
✅ 验证方式可执行的正确性与性能验收标准逐条验证后勾选，进度保存在浏览器本地（左侧进度条）
📦 阶段性产出本阶段结束时应留下的代码、数据与报告每阶段打一个 git tag，性能数据写入 bench/results/
前置知识：熟悉 C++17（模板、指针、内存布局）和 Python；了解 Transformer 推理流程（Prefill / Decode、KV Cache、GQA、RoPE、SwiGLU、MoE）；会用 PyTorch。不要求有 CUDA 经验。
关于性能阈值：验收中给出的百分比（如“达到 cuBLAS 的 80%”）都是建议起点，基于同一块 GPU、同一形状、同一精度对比。实际数值会随 SKU、功耗上限、频率和驱动版本变化，请以自己机器上的基线为准。文中的硬件规格均为约值，以 NVIDIA 官方 datasheet 和 deviceQuery 实测为准。
学习方法：每个算子都按“先写对，再写快”推进：先实现 PyTorch 参考版本和正确性测试，再写朴素 kernel，然后逐级优化。每一次优化都要回答两个问题：它解决了 Nsight Compute 里的哪个瓶颈指标？提升是否和理论预期一致？

ii. 学习路线全景

路线按“基础访存 → 计算密集的 GEMM → 推理专用算子 → 系统级优化”递进。每个阶段只引入一两个新机制，并且直接复用上一阶段的代码：阶段 3 的 warp 归约会用在阶段 4 的归一化、阶段 9 的 GEMV、阶段 11 的 decode attention；阶段 6–7 的 Tensor Core 流水线是阶段 10 FlashAttention 和阶段 12 Grouped GEMM 的基础。

iii. GPU 架构演进与硬件特性

两个数字决定了大部分优化方向。以 H100 为例，BF16 稠密算力约 990 TFLOPS，显存带宽约 3.35 TB/s，平衡点约为 300 FLOP/Byte：算术强度低于这个值的算子受带宽限制，高于它的受算力限制。Decode 阶段 batch=1 的 GEMV 算术强度约为 1 FLOP/Byte，比平衡点低两个数量级，所以 decode 优化的重点是“少读字节”（量化、融合、KV 复用），而不是“多用 Tensor Core”。

环境准备与架构认知

写第一个 kernel 之前，先确认工具链、摸清手上 GPU 的参数，并搭好计时与正确性测试框架。

难度 ★参考用时 1 天产出 v0.0任意 NVIDIA 数据中心 GPU
本阶段的位置：后面每个阶段都要回答“比理论上限差多少”。这需要两样东西：本机 GPU 的理论峰值，以及一个可信的计时框架。这里的 device_info 和 bench/util.py 会一直用到结业项目。

🎯学习目标

  • 理解 GPU 执行模型：SM、warp（32 线程）、warp 调度器、SIMT
  • 理解 Compute Capability、PTX 与 SASS、fatbinary 和 -gencode 的关系
  • 知道 Driver、CUDA Toolkit、PyTorch 的 CUDA 版本三者之间的兼容规则
  • 认识工具：nvcc、compute-sanitizer、Nsight Systems（时间线）、Nsight Compute（单 kernel 剖析）

🛠需实现的功能

  • scripts/env_check.sh：打印驱动、Toolkit、GPU 型号、Compute Capability、PyTorch 的 CUDA 版本
  • tools/device_info.cu：输出 SM 数、Shared Memory 上限、L2 大小、寄存器数，并计算理论显存带宽
  • CMakeLists.txt：按 GPU 选择 CMAKE_CUDA_ARCHITECTURES（80 / 90a / 100a / 103a）
  • bench/util.py：统一的 warmup + CUDA Event 计时、带宽与 TFLOPS 换算、结果写入 CSV

💡实践要点

  • B200 需要 CUDA 12.8+，B300 需要 CUDA 12.9+；PyTorch 要选对应的 wheel（如 cu128 或更新），否则会出现“no kernel image is available”
  • 理论带宽 = 2 × 显存时钟 × 位宽 / 8。CUDA 13 移除了 cudaDeviceProp::memoryClockRate 等字段，统一改用 cudaDeviceGetAttribute 查询
  • 多架构发布时同时嵌入 SASS 和 PTX：-gencode arch=compute_80,code=[sm_80,compute_80]，保证新卡能 JIT 运行
  • 编译时始终加 -lineinfo：Nsight Compute 才能把指标对应到源码行，且几乎不影响性能
  • 没有 Hopper / Blackwell 的话，可以按小时租用云 GPU，只在阶段 8、9、13 的相关实验中使用

✅验证方式

  • nvidia-smi 显示 GPU 型号与 Compute Capability，驱动版本满足 Toolkit 要求
  • device_info 计算出的理论带宽与 datasheet 相差不超过 5%
  • python -c "import torch; print(torch.cuda.get_device_capability())" 输出与本机一致
  • 用 compute-sanitizer 运行一个故意越界的小 kernel，能够报出越界错误

// tools/device_info.cu —— nvcc -O2 -o device_info device_info.cu
#include <cstdio>
#include <cuda_runtime.h>

int main() {
  int dev = 0;
  cudaDeviceProp p;
  cudaGetDeviceProperties(&p, dev);
  int mem_clk_khz, bus_bits, smem_optin;
  cudaDeviceGetAttribute(&mem_clk_khz, cudaDevAttrMemoryClockRate, dev);
  cudaDeviceGetAttribute(&bus_bits, cudaDevAttrGlobalMemoryBusWidth, dev);
  cudaDeviceGetAttribute(&smem_optin, cudaDevAttrMaxSharedMemoryPerBlockOptin, dev);

  printf("GPU %s | CC %d.%d | SMs %d\n", p.name, p.major, p.minor, p.multiProcessorCount);
  printf("L2 %.1f MB | smem/SM %zu KB | smem/block(opt-in) %d KB | regs/SM %d\n",
         p.l2CacheSize / 1048576.0, p.sharedMemPerMultiprocessor / 1024,
         smem_optin / 1024, p.regsPerMultiprocessor);
  printf("Theoretical DRAM BW: %.0f GB/s\n", 2.0 * mem_clk_khz * 1e3 * (bus_bits / 8) / 1e9);
}
# bench/util.py —— 所有基准共用的计时工具
import torch

def bench(fn, warmup=20, iters=100):
    for _ in range(warmup):
        fn()
    torch.cuda.synchronize()
    st = torch.cuda.Event(enable_timing=True)
    ed = torch.cuda.Event(enable_timing=True)
    st.record()
    for _ in range(iters):
        fn()
    ed.record()
    torch.cuda.synchronize()
    return st.elapsed_time(ed) / iters          # 毫秒

def report(name, ms, bytes_moved=0, flops=0):
    gbps = bytes_moved / ms / 1e6 if bytes_moved else 0.0
    tflops = flops / ms / 1e9 if flops else 0.0
    print(f"{name:<32}{ms * 1e3:10.1f} us {gbps:9.0f} GB/s {tflops:8.1f} TFLOPS")

第一个 Kernel：向量加法与执行模型

最简单的算子，用来建立“线程如何映射到数据”和“如何正确计时”的基本功。

难度 ★参考用时 1 天A100 即可
承上启下：用阶段 0 的计时框架，第一次测出“有效带宽 / 理论带宽”。向量加法几乎没有计算，它能跑到的带宽就是后续所有访存类算子的现实上限。

🎯学习目标

  • 掌握 grid、block、thread 三级层次，以及 blockIdx、threadIdx、blockDim 的索引计算
  • 理解 kernel launch 是异步的：错误要用 cudaGetLastError 和同步来捕获
  • 理解 grid-stride loop：一个 kernel 适配任意数据规模
  • 理解为什么 128-bit 向量化读写（float4）能减少指令数、提高带宽

🛠需实现的功能

  • csrc/common.cuh：CUDA_CHECK 宏、cdiv 等工具
  • vec_add 三个版本：一个线程处理一个元素 → grid-stride loop → float4 向量化（含尾部处理）
  • 用 CUDA Event 计时，输出耗时和有效带宽 = 3 × N × 4 B / 时间
  • 扫描 block 大小（64 / 128 / 256 / 512 / 1024），记录带宽变化

💡实践要点

// in: M×N（行主序） → out: N×M；block = (TILE, ROWS)，grid = (cdiv(N, TILE), cdiv(M, TILE))
template <int TILE = 32, int ROWS = 8>
__global__ void transpose_smem(const float* __restrict__ in, float* __restrict__ out, int M, int N) {
  __shared__ float tile[TILE][TILE + 1];               // +1 让同一列落在不同 bank
  int x = blockIdx.x * TILE + threadIdx.x;
  int y = blockIdx.y * TILE + threadIdx.y;
  for (int j = 0; j < TILE; j += ROWS)
    if (x < N && y + j < M) tile[threadIdx.y + j][threadIdx.x] = in[(size_t)(y + j) * N + x];
  __syncthreads();

  x = blockIdx.y * TILE + threadIdx.x;                 // 交换 block 坐标，使写出也是合并的
  y = blockIdx.x * TILE + threadIdx.y;
  for (int j = 0; j < TILE; j += ROWS)
    if (x < M && y + j < N) out[(size_t)(y + j) * M + x] = tile[threadIdx.x][threadIdx.y + j];
}

归约、Warp 原语与 Softmax

归约是推理算子中出现最多的计算模式：Softmax、Norm、Attention、Top-K 都离不开它。

🎯学习目标

  • 树形归约、warp divergence，以及为什么最后 32 个元素交给 warp shuffle 做

  • 数值稳定性：safe softmax（减最大值），以及 online softmax 如何一趟同时得到最大值和归一化分母

🛠需实现的功能

  • 求和归约三个版本：Shared Memory 树形 → warp shuffle → 向量化 + grid-stride + 两趟归约
  • 行 Softmax 两种调度：一个 warp 处理一行（行长 ≤ 1024，如 attention score）；一个 block 处理一行（词表 32K–256K 的 logits）
  • Online softmax 版本：一趟读取同时求 max 和 sum，再一趟写出，读取次数从 3 次减到 2 次

// common.cuh：warp 内蝶形归约，结果广播到所有 lane
__device__ __forceinline__ float warp_reduce_sum(float v) {
  #pragma unroll
  for (int o = 16; o > 0; o >>= 1) v += __shfl_xor_sync(0xffffffff, v, o);
  return v;
}
__device__ __forceinline__ float warp_reduce_max(float v) {
  #pragma unroll
  for (int o = 16; o > 0; o >>= 1) v = fmaxf(v, __shfl_xor_sync(0xffffffff, v, o));
  return v;
}

// block 归约：先 warp 内，再由 warp 0 归约各 warp 的部分和，最后广播给全部线程
__device__ float block_reduce_sum(float v) {
  __shared__ float partial[32];
  __shared__ float total;
  int lane = threadIdx.x & 31, wid = threadIdx.x >> 5;
  v = warp_reduce_sum(v);
  if (lane == 0) partial[wid] = v;
  __syncthreads();
  if (wid == 0) {
    int nw = (blockDim.x + 31) >> 5;
    v = warp_reduce_sum(lane < nw ? partial[lane] : 0.f);
    if (lane == 0) total = v;
  }
  __syncthreads();
  return total;
}
// online softmax：每个线程维护 (m = 当前最大值, d = 以 m 为基准的指数和)，两两合并
struct MD { float m, d; };

__device__ __forceinline__ MD md_merge(MD a, MD b) {
  float m = fmaxf(a.m, b.m);
  return {m, a.d * __expf(a.m - m) + b.d * __expf(b.m - m)};
}

// 一个 warp 处理一行，row 长度为 n
__global__ void softmax_warp_row(const float* __restrict__ x, float* __restrict__ y, int rows, int n) {
  int row = blockIdx.x * (blockDim.x / 32) + threadIdx.x / 32, lane = threadIdx.x % 32;
  if (row >= rows) return;
  const float* xr = x + (size_t)row * n;
  MD md{-FLT_MAX, 0.f};
  for (int i = lane; i < n; i += 32) md = md_merge(md, {xr[i], 1.f});     // 第 1 趟：读
  #pragma unroll
  for (int o = 16; o > 0; o >>= 1) {
    MD other{__shfl_xor_sync(0xffffffff, md.m, o), __shfl_xor_sync(0xffffffff, md.d, o)};
    md = md_merge(md, other);
  }
  float inv = 1.f / md.d;
  for (int i = lane; i < n; i += 32) y[(size_t)row * n + i] = __expf(xr[i] - md.m) * inv;  // 第 2 趟：写
}

// csrc/norm/rmsnorm.cu —— 要求 hidden % 8 == 0 且指针 16 字节对齐
#include <cuda_bf16.h>
#include "../common.cuh"

template <int VEC = 8>
__global__ void rmsnorm_bf16(const __nv_bfloat16* __restrict__ x, const __nv_bfloat16* __restrict__ w,
                             __nv_bfloat16* __restrict__ y, int hidden, float eps) {
  const __nv_bfloat16* xr = x + (size_t)blockIdx.x * hidden;
  __nv_bfloat16* yr = y + (size_t)blockIdx.x * hidden;

  float ss = 0.f;
  for (int i = threadIdx.x * VEC; i < hidden; i += blockDim.x * VEC) {
    uint4 pk = *reinterpret_cast<const uint4*>(xr + i);            // 一次读 8 个 bf16
    auto* h2 = reinterpret_cast<const __nv_bfloat162*>(&pk);
    #pragma unroll
    for (int k = 0; k < VEC / 2; ++k) {
      float2 f = __bfloat1622float2(h2[k]);
      ss += f.x * f.x + f.y * f.y;
    }
  }
  float inv = rsqrtf(block_reduce_sum(ss) / hidden + eps);

  for (int i = threadIdx.x * VEC; i < hidden; i += blockDim.x * VEC) {
    uint4 px = *reinterpret_cast<const uint4*>(xr + i);
    uint4 pw = *reinterpret_cast<const uint4*>(w + i);
    uint4 po;
    auto* hx = reinterpret_cast<const __nv_bfloat162*>(&px);
    auto* hw = reinterpret_cast<const __nv_bfloat162*>(&pw);
    auto* ho = reinterpret_cast<__nv_bfloat162*>(&po);
    #pragma unroll
    for (int k = 0; k < VEC / 2; ++k) {
      float2 fx = __bfloat1622float2(hx[k]), fw = __bfloat1622float2(hw[k]);
      ho[k] = __floats2bfloat162_rn(fx.x * inv * fw.x, fx.y * inv * fw.y);
    }
    *reinterpret_cast<uint4*>(yr + i) = po;
  }
}

void launch_rmsnorm(const __nv_bfloat16* x, const __nv_bfloat16* w, __nv_bfloat16* y,
                    int rows, int hidden, float eps, cudaStream_t stream) {
  rmsnorm_bf16<8><<<rows, 256, 0, stream>>>(x, w, y, hidden, eps);
}

用 FP32 CUDA Core 一步步把矩阵乘从 1% 推到 cuBLAS 的 70% 以上，理解“分块层次”这一贯穿所有 GEMM 的思想。

🎯学习目标

  • GEMM 的算术强度如何随分块尺寸增长：每一层分块都在提高数据复用率
  • 寄存器分块（thread tile）：一个线程计算 8×8 个输出，把 Shared Memory 读取量降低一个数量级
  • 寄存器压力与 spill：如何从 ptxas -v 输出看寄存器数和溢出
  • 双缓冲（double buffering）的思想：计算当前 tile 的同时加载下一个 tile

🛠需实现的功能

  • 按顺序实现并保留：朴素版 → 合并访存版 → Shared Memory 分块版 → 1D 寄存器分块 → 2D 寄存器分块（BM=BN=128, BK=8, TM=TN=8）→ 向量化 + A 转置存储 → warp 分块

  • 形状扫描：方阵 512–8192，以及 LLM 常见形状（如 M=4096, N=4096, K=4096 和 K=14336）

💡实践要点

  • 加 -Xptxas -v 检查每个线程的寄存器数和 spill；有 spill 时先减小 thread tile 尺寸
  • A tile 在 Shared Memory 中转置存储（As[BK][BM]），使内层循环按连续地址读取并能用 float4
  • 用 __launch_bounds__(256) 告诉编译器 block 大小，帮助寄存器分配

// C = A·B，行主序：A[M×K]、B[K×N]；block = (32, 32)
template <int T = 32>
__global__ void sgemm_smem(int M, int N, int K, const float* __restrict__ A,
                           const float* __restrict__ B, float* __restrict__ C) {
  __shared__ float As[T][T], Bs[T][T];
  int row = blockIdx.y * T + threadIdx.y, col = blockIdx.x * T + threadIdx.x;
  float acc = 0.f;
  for (int k0 = 0; k0 < K; k0 += T) {
    As[threadIdx.y][threadIdx.x] = (row < M && k0 + threadIdx.x < K) ? A[(size_t)row * K + k0 + threadIdx.x] : 0.f;
    Bs[threadIdx.y][threadIdx.x] = (col < N && k0 + threadIdx.y < K) ? B[(size_t)(k0 + threadIdx.y) * N + col] : 0.f;
    __syncthreads();
    #pragma unroll
    for (int k = 0; k < T; ++k) acc += As[threadIdx.y][k] * Bs[k][threadIdx.x];
    __syncthreads();
  }
  if (row < M && col < N) C[(size_t)row * N + col] = acc;
}

float acc[TM][TN] = {}, a_frag[TM], b_frag[TN];
#pragma unroll
for (int k = 0; k < BK; ++k) {
  #pragma unroll
  for (int i = 0; i < TM; ++i) a_frag[i] = As[k][ty * TM + i];
  #pragma unroll
  for (int j = 0; j < TN; ++j) b_frag[j] = Bs[k][tx * TN + j];
  #pragma unroll
  for (int i = 0; i < TM; ++i)
    #pragma unroll
    for (int j = 0; j < TN; ++j) acc[i][j] += a_frag[i] * b_frag[j];   // 读 TM+TN 个数，做 TM×TN 次 FMA
}

Tensor Core 入门：WMMA 与 mma.sync

从高层 WMMA API 进入 PTX 级 mma.sync 与 ldmatrix，掌握 Ampere Tensor Core 的数据布局。

难度 ★★★参考用时 3 天A100 即可（sm_80+）
承上启下：沿用阶段 5 的分块结构，把最内层的 FP32 FMA 换成 BF16 Tensor Core 指令，理论算力从 19.5 TFLOPS 提升到 312 TFLOPS（A100）。这时瓶颈会迅速转移到“数据供给”，这正是阶段 7 要解决的问题。

🎯学习目标

  • Tensor Core 的计算单位：一条 warp 级指令完成一个小矩阵乘（如 m16n8k16）
  • Fragment 布局：每个 lane 持有矩阵的哪些元素（参见 PTX ISA 中的布局图）
  • ldmatrix：一条指令从 Shared Memory 加载 4 个 8×8 矩阵，直接得到 MMA 所需的寄存器布局
  • Swizzle 布局：对 Shared Memory 地址做 XOR 变换，让 ldmatrix 不产生 bank conflict
  • 推理中常用的 “TN” 布局：Y = X · Wᵀ，W 为 [N, K] 行主序（即 nn.Linear 的权重）

🛠需实现的功能

  • hgemm_wmma：每个 warp 计算 16×16 输出，BF16 输入、FP32 累加
  • hgemm_mma：block tile 128×128×32，8 个 warp，warp tile 64×32；ldmatrix + mma.sync.m16n8k16
  • Shared Memory 采用 XOR swizzle 布局；epilogue 把 FP32 累加器转成 BF16 并向量化写回
  • 与 torch.matmul（cuBLAS）对比，覆盖 LLM 线性层形状

💡实践要点

  • 先用 WMMA 跑通正确性，再换成 PTX；每次只改一处，用单元测试兜底
  • ldmatrix 的每个 lane 提供一行的地址：lane 0–7 对应第 1 个 8×8 矩阵，8–15 对应第 2 个，以此类推
  • Shared Memory 指针要先用 __cvta_generic_to_shared 转成 32 位共享地址，再传给内联 PTX
  • 本阶段先用同步的全局 → 共享内存拷贝，Tensor Core 利用率不高是预期现象，阶段 7 再解决
  • BF16 的有效精度只有 8 位，参考结果应该用“BF16 输入、FP32 累加”计算，而不是 FP32 输入

✅验证方式

  • 两个版本与 torch.matmul（BF16）对比，相对误差小于 1e-2，覆盖 M ∈ {16, 128, 4096}、N/K ∈ {4096, 14336}
  • 4096³ BF16：WMMA 版达到 cuBLAS 的 30% 以上，mma.sync + ldmatrix 版达到 50% 以上
  • Nsight Compute 中 swizzle 版的 Shared Memory bank conflict 接近 0，Tensor 管线利用率（sm__pipe_tensor_op_hmma_cycles_active）明显上升
  • 能在纸上画出 m16n8k16 中 A、B、C fragment 的 lane 分布

// 要求 M、N、K 是 16 的倍数；blockDim = (128, 4)，每个 block 16 个 warp，覆盖 64×64 输出
#include <mma.h>
#include <cuda_bf16.h>
using namespace nvcuda;

__global__ void hgemm_wmma(const __nv_bfloat16* A, const __nv_bfloat16* B, float* C, int M, int N, int K) {
  int warp_n = (blockIdx.x * blockDim.x + threadIdx.x) / 32;
  int warp_m = blockIdx.y * blockDim.y + threadIdx.y;
  int m0 = warp_m * 16, n0 = warp_n * 16;
  if (m0 >= M || n0 >= N) return;

  wmma::fragment<wmma::matrix_a, 16, 16, 16, __nv_bfloat16, wmma::row_major> a;
  wmma::fragment<wmma::matrix_b, 16, 16, 16, __nv_bfloat16, wmma::col_major> b;
  wmma::fragment<wmma::accumulator, 16, 16, 16, float> c;
  wmma::fill_fragment(c, 0.f);
  for (int k0 = 0; k0 < K; k0 += 16) {
    wmma::load_matrix_sync(a, A + (size_t)m0 * K + k0, K);
    wmma::load_matrix_sync(b, B + (size_t)n0 * K + k0, K);   // 列主序 B 的 (k0, n0) 位置
    wmma::mma_sync(c, a, b, c);
  }
  wmma::store_matrix_sync(C + (size_t)m0 * N + n0, c, N, wmma::mem_row_major);
}

异步拷贝与多级软件流水线

用 Ampere 的 cp.async 让数据搬运和 Tensor Core 计算重叠，把 HGEMM 推到 cuBLAS 的 80% 以上。

难度 ★★★★参考用时 4 天产出 v0.2A100 即可（sm_80+）
承上启下：阶段 6 的 kernel 中，warp 在等全局内存时 Tensor Core 是空闲的。cp.async 让全局 → 共享内存的拷贝不经过寄存器、不阻塞线程，配合多级缓冲就能把加载延迟完全隐藏。这套“多 stage 流水线”的写法会直接复用到阶段 10 和阶段 12。

🎯学习目标

  • cp.async.cg（只经过 L2、16 字节）与 cp.async.ca 的区别
  • commit_group / wait_group N 的语义：允许最多 N 组拷贝仍在进行
  • 多级流水线：用 3–4 个 Shared Memory 缓冲区，计算第 k 块时预取第 k+S−1 块
  • 超过 48 KB 的动态 Shared Memory 需要显式申请；stage 数与 occupancy 的权衡
  • Threadblock swizzle（光栅化顺序）如何提高 L2 命中率；小 M 时的 Split-K

🛠需实现的功能

  • hgemm_pipeline：cp.async + 3/4 stage 流水线 + 寄存器级双缓冲（提前 ldmatrix 下一个 k 片）
  • 边界处理：用 cp.async 的 src-size 参数对越界部分填 0
  • Threadblock swizzle 与 Split-K（M ≤ 64 时）
  • 简单的 autotune：在 (BM, BN, BK, STAGES, warp 数) 候选配置中，按形状选最快的并缓存结果

💡实践要点

  • 即使当前迭代没有发起拷贝也要 commit 一个空组，否则 wait_group 的计数会错位
  • 迭代开始时的 __syncthreads() 同时保证两件事：当前 stage 的数据对所有线程可见；即将被覆盖的 stage 已经没有线程在读

  • 全局地址必须 16 字节对齐；K 不是 8 的倍数（BF16）时退回到慢速路径

✅验证方式

  • stage 数 2 / 3 / 4 的对比表，并用 ncu 的 stall 原因解释差异
  • M ≤ 64 时启用 Split-K 后速度明显提升

Hopper / Blackwell 新特性：TMA、WGMMA、tcgen05 与 TMEM

理解新一代 GPU 的“异步数据流”编程模型，用 CuTe / CUTLASS 写出接近峰值的 H100 与 B200 / B300 GEMM。

难度 ★★★★★参考用时 6–7 天需 H100（sm_90a）或 B200 / B300（sm_100a / sm_103a）
承上启下：阶段 7 中每个线程都要计算地址、发起拷贝、执行 MMA。Hopper 和 Blackwell 把这些工作交给专用硬件：TMA 负责搬整块张量，MMA 变成异步指令，由少数线程发起。编程方式因此从“所有 warp 做同样的事”变成“不同 warp 分工协作”（warp specialization）。直接手写 PTX 的门槛很高，本阶段以读懂并使用 CuTe / CUTLASS 为主。

🎯学习目标

  • TMA：host 端创建 tensor map 描述符，device 端一个线程发起整块 2D/3D 拷贝，并支持硬件 swizzle 和 cluster 内多播
  • mbarrier：基于“到达计数 + 事务字节数”的异步屏障，以及 phase（相位）翻转
  • Thread Block Cluster 与分布式 Shared Memory：同一 cluster 内的 block 可以互相读写 Shared Memory
  • WGMMA（Hopper）：4 个 warp 组成的 warpgroup 发起异步 MMA，操作数通过 Shared Memory 描述符读取
  • tcgen05（Blackwell）：单线程发起 MMA，累加器放在 TMEM 中，寄存器被释放给 epilogue；cta_group::2 让两个 SM 协同计算一个更大的 tile
  • Warp specialization 与 persistent kernel：producer warp 负责 TMA，consumer warp 负责 MMA，通过 mbarrier 环形缓冲协作

🛠需实现的功能

  • tma_copy：用 TMA + cuda::barrier 搬运 2D tile，与阶段 7 的 cp.async 版本比较带宽和发起拷贝的线程数
  • cluster_reduce：2–4 个 block 组成 cluster，通过分布式 Shared Memory 完成跨 block 归约
  • 基于 CUTLASS 3.x / 4.x 的 sm90 GEMM（TMA + WGMMA + warp specialization）与 sm100 GEMM（TMA + tcgen05 + TMEM），从 CUTLASS 示例出发，改成 TN 布局、BF16 输出并加入 bias epilogue

  • 必须用 sm_90a / sm_100a / sm_103a 编译才能使用这些指令，且不同架构之间不兼容，需要按架构分发

// device 端：一个线程发起 TMA，所有线程在 cuda::barrier 上等待（sm_90+）
#include <cuda.h>
#include <cuda/barrier>
#include <cuda_bf16.h>
using barrier = cuda::barrier<cuda::thread_scope_block>;
namespace cde = cuda::device::experimental;

constexpr int TILE_M = 64, TILE_N = 64;

__global__ void tma_load_tile(const __grid_constant__ CUtensorMap tmap, __nv_bfloat16* out) {
  __shared__ alignas(128) __nv_bfloat16 tile[TILE_M][TILE_N];
  #pragma nv_diag_suppress static_var_with_dynamic_init
  __shared__ barrier bar;
  if (threadIdx.x == 0) {
    init(&bar, blockDim.x);
    cde::fence_proxy_async_shared_cta();          // 让 barrier 的初始化对 TMA（异步代理）可见
  }
  __syncthreads();

  int x = blockIdx.x * TILE_N, y = blockIdx.y * TILE_M;   // x 为最内层维度（列）
  barrier::arrival_token token;
  if (threadIdx.x == 0) {
    cde::cp_async_bulk_tensor_2d_global_to_shared(&tile, &tmap, x, y, bar);
    token = cuda::device::barrier_arrive_tx(bar, 1, sizeof(tile));   // 声明本轮期望到达的字节数
  } else {
    token = bar.arrive();

Decode GEMV 与量化 GEMM

Decode 阶段的线性层受读权重的带宽限制：权重读得越少，生成越快。

难度 ★★★★参考用时 4 天产出 v0.3GEMV / W4A16：A100FP8：H100+ · NVFP4：B200 / B300
承上启下：阶段 5–8 优化的是大 M 的算力受限 GEMM；Decode 时 M 只有 1 到几十，算术强度骤降，又回到阶段 1–4 的带宽受限场景。本阶段结合两者：用阶段 3 的 warp 归约写 GEMV，用阶段 6–7 的 Tensor Core 流水线写小 batch 量化 GEMM，用阶段 8 的 Blackwell 硬件做 NVFP4。

🎯学习目标

  • Decode GEMV 的性能上限 = 权重字节数 / 显存带宽；BF16 → INT4 理论上可提速约 4 倍
  • Weight-only 量化（W4A16、W8A16）与权重 + 激活量化（W8A8、FP8）的适用场景
  • Group-wise 量化：每 64 或 128 个元素共享一个 scale，以及反量化开销如何隐藏在访存中
  • FP8（E4M3 / E5M2）的 per-tensor、per-token、per-block scale 策略
  • Blackwell 微缩放格式：MXFP8 / MXFP4 每 32 个元素共享一个 E8M0 scale；NVFP4 每 16 个元素共享一个 FP8 E4M3 scale，再加一个 FP32 全局 scale

🛠需实现的功能

  • gemv_bf16：每个 warp 负责一行权重，16 字节向量化读取，warp 归约
  • gemv_w4a16：INT4 权重 + group size 128 的 FP16 scale；Python 端的离线量化与打包脚本
  • 小 batch（M ≤ 16）W4A16 GEMM：在寄存器中反量化后送入 mma.sync（Marlin 思路）
  • 动态 per-token FP8 激活量化 kernel（可融合进阶段 4 的 RMSNorm）+ 调用 cuBLASLt / CUTLASS 的 FP8 GEMM（H100+）
  • 在 B200 / B300 上基于 CUTLASS block-scaled 示例跑通 NVFP4 GEMM，并与 FP8、BF16 对比

💡实践要点

  • 离线重排权重布局，让每个线程一次读到 16 字节连续的量化数据；scale 预先放进 Shared Memory 或寄存器
  • INT4 → FP16 可以用位运算技巧（把 4 位值拼进 FP16 尾数，再减去魔数）代替整数转浮点指令，配合 lop3 一条指令完成
  • 量化 kernel 的正确性要和“反量化后的参考结果”比较，而不是和原始 FP16 权重比较，否则量化误差会掩盖 kernel bug
  • N 较小、SM 填不满时用 Split-K，让更多 block 同时读权重
  • B300 削减了 INT8 Tensor Core 吞吐，新部署应优先考虑 FP8 / NVFP4 方案

✅验证方式

  • 形状 4096×14336 时，gemv_bf16 带宽达到峰值的 80% 以上
  • gemv_w4a16 与反量化参考的相对误差小于 1e-3，同形状下比 gemv_bf16 快 2.5 倍以上
  • M ∈ {1, 4, 16} 时，W4A16 GEMM 快于 cuBLAS BF16 GEMM
  • （H100+）FP8 GEMM 的 TFLOPS 与 BF16 对比；（B200 / B300）NVFP4 GEMM 的 TFLOPS 与 FP8 对比，并给出各自的量化误差

// W: [N, K/8] uint32，每个 uint32 打包 8 个 int4（低位在前，零点为 8）
// scales: [N, K/G] half；x: [K] half；y: [N] half；每个 warp 负责一行
template <int G = 128>
__global__ void gemv_w4a16(const uint32_t* __restrict__ W, const half* __restrict__ scales,
                           const half* __restrict__ x, half* __restrict__ y, int N, int K) {
  int row = blockIdx.x * (blockDim.x / 32) + (threadIdx.x >> 5);
  int lane = threadIdx.x & 31;
  if (row >= N) return;
  const uint32_t* wr = W + (size_t)row * (K / 8);
  const half* sr = scales + (size_t)row * (K / G);

  float acc = 0.f;
  for (int p = lane; p < K / 8; p += 32) {
    uint32_t pk = wr[p];
    float s = __half2float(sr[(p * 8) / G]);
    #pragma unroll
    for (int j = 0; j < 8; ++j) {
      int q = (pk >> (4 * j)) & 0xF;
      acc += (q - 8) * s * __half2float(x[p * 8 + j]);
    }
  }
  acc = warp_reduce_sum(acc);
  if (lane == 0) y[row] = __float2half(acc);
}

# python/infer_kernels/quantize.py —— 对称 group-wise INT4 量化与打包（参考实现）
def quantize_w4(w: torch.Tensor, group: int = 128):
    N, K = w.shape
    wg = w.float().view(N, K // group, group)
    scale = wg.abs().amax(-1, keepdim=True).clamp(min=1e-8) / 7.0
    q = (wg / scale).round().clamp(-8, 7).to(torch.int32) + 8          # 0..15
    q = q.view(N, K // 8, 8)
    packed = torch.zeros(N, K // 8, dtype=torch.int32, device=w.device)
    for j in range(8):
        packed |= q[..., j] << (4 * j)
    return packed, scale.view(N, K // group).half()

FlashAttention（Prefill）

用分块和 online softmax 把注意力的显存占用从 O(N²) 降到 O(N)，并让它跑在 Tensor Core 上。

难度 ★★★★★参考用时 6–7 天产出 v0.4A100 即可（FA2 风格）
承上启下：这是前面所有技能的综合：阶段 3 的 online softmax、阶段 6 的 mma.sync 与 ldmatrix、阶段 7 的 cp.async 流水线。理解阶段 8 的 warp specialization 之后，还能读懂 FlashAttention-3（Hopper）和 FlashAttention-4（Blackwell）的设计。

🎯学习目标

  • 标准注意力的问题：N×N 的分数矩阵要写回显存再读出来
  • FlashAttention 的分块：Q 按行分块常驻，遍历 K/V 块，用 online softmax 在线修正已累加的输出
  • FA2 的并行策略：沿序列方向并行 Q 块，各 warp 分别负责不同的 Q 行，避免 warp 间的归约
  • Causal mask：完全被 mask 的块直接跳过，只有对角块逐元素 mask
  • FA3（Hopper）：producer / consumer warp specialization、两个 warpgroup 间 ping-pong 调度、softmax 与 GEMM 重叠、FP8
  • FA4（Blackwell）：TMEM 存放累加器、用 FMA 多项式模拟部分 exp2、只在最大值显著变化时才重新缩放输出；B300 的 SFU exp 吞吐翻倍会改变 softmax 的瓶颈

🛠需实现的功能

  • attn_naive：QKᵀ → softmax → PV 三个 kernel，作为正确性和性能基线
  • flash_attn_fwd：BF16，head_dim 64 / 128，Br = Bc = 64，4 个 warp（每个 warp 负责 16 行 Q）
  • K/V 块使用 cp.async 双缓冲；P 不经过 Shared Memory，直接从累加器寄存器转换为第二个 MMA 的 A 操作数
  • 支持 causal 与 non-causal、GQA（多个 Q 头共享一组 KV）、任意序列长度；输出 LSE（log-sum-exp），供阶段 11 合并使用
  • 可选：varlen 接口（cu_seqlens），支持把多条不等长序列拼在一起做 prefill

💡实践要点

  • 把 softmax_scale × log2(e) 合并成一个常数，统一用 exp2f
  • m16n8 累加器中，同一行的元素分布在 4 个相邻 lane 上，行最大值和行和用两次 __shfl_xor_sync（偏移 1 和 2）完成
  • m16n8k16 累加器的寄存器布局与 A 操作数布局兼容，转成 BF16 打包即可作为 PV 的 A 输入，省掉一次 Shared Memory 往返
  • 行和 l 在循环中只做线程内累加，循环结束后再做一次 4 lane 归约
  • 整行都被 mask 时最大值为 -inf，要特殊处理以避免 NaN；序列长度不是块大小的倍数时，越界的 K 位置要按 mask 处理
  • FLOPs 计算：non-causal 为 4·B·H·N²·d，causal 约为一半

✅验证方式

  • 与 FP32 参考实现（torch.nn.functional.scaled_dot_product_attention 的 math 后端）对比，BF16 最大绝对误差小于 2e-2；覆盖序列长度 {1, 17, 128, 1000, 4096, 16384}、causal / non-causal、GQA
  • LSE 输出与参考一致（误差小于 1e-3）
  • A100、seqlen 4096、head_dim 128 时达到 FlashAttention-2 官方实现 TFLOPS 的 50% 以上
  • 序列长度 64K 时可正常运行，显存占用随长度线性增长（attn_naive 会 OOM）

# FlashAttention 前向（单个 Q 块 Q_i）
m = -inf, l = 0, O = 0
for j in KV 块:                               # causal 时只遍历到对角块
    S     = Q_i @ K_j^T * scale                # Tensor Core
    m_new = max(m, rowmax(S))
    P     = exp(S - m_new)
    alpha = exp(m - m_new)                     # 修正之前的累加结果
    l     = l * alpha + rowsum(P)
    O     = O * alpha + P @ V_j                # Tensor Core
    m     = m_new
O = O / l;  LSE = m + log(l)
// kernel 主循环结构（省略加载与 fragment 细节）：每个 warp 负责 16 行 Q
// m16n8 累加器中每个线程覆盖 2 行：s[t][0..1] 属于第 lane/4 行，s[t][2..3] 属于第 lane/4+8 行
float m[2] = {-INFINITY, -INFINITY}, l[2] = {0.f, 0.f};
float o_acc[D / 8][4] = {};
const float scale_log2 = softmax_scale * 1.4426950408889634f;

for (int j = 0; j < n_kv_blocks; ++j) {
  // cp.async 预取 K_{j+1}、V_{j+1}；等待 K_j 就绪
  float s[Bc / 8][4] = {};
  mma_qk(s, q_frag, sK);                                   // S = Q K^T（16 × Bc）
  if (is_diagonal_or_tail(j)) apply_mask(s, j);            // 越界或 causal 位置置为 -inf
  #pragma unroll
  for (int r = 0; r < 2; ++r) {
    float mx = m[r];
    for (int t = 0; t < Bc / 8; ++t) mx = fmaxf(mx, fmaxf(s[t][2 * r], s[t][2 * r + 1]));
    mx = fmaxf(mx, __shfl_xor_sync(0xffffffff, mx, 1));    // 同一行分布在 4 个 lane 上
    mx = fmaxf(mx, __shfl_xor_sync(0xffffffff, mx, 2));
    float m_s = (mx == -INFINITY) ? 0.f : mx * scale_log2;   // 整行被 mask 时避免 NaN
    float alpha = exp2f(m[r] * scale_log2 - m_s);
    float rs = 0.f;
    for (int t = 0; t < Bc / 8; ++t) {
      s[t][2 * r]     = exp2f(s[t][2 * r]     * scale_log2 - m_s);
      s[t][2 * r + 1] = exp2f(s[t][2 * r + 1] * scale_log2 - m_s);
      rs += s[t][2 * r] + s[t][2 * r + 1];
    }
    l[r] = l[r] * alpha + rs;                              // 线程内部分和，循环结束后再做 4 lane 归约
    for (int t = 0; t < D / 8; ++t) { o_acc[t][2 * r] *= alpha; o_acc[t][2 * r + 1] *= alpha; }
    m[r] = mx;
  }
  // 等待 V_j 就绪；P 从累加器布局直接打包为 bf16 A fragment
  mma_pv(o_acc, pack_bf16(s), sV);                         // O += P V
}

Decode Attention 与 Paged KV Cache

逐 token 生成时，注意力的瓶颈是读 KV Cache。本阶段实现 vLLM 式的分页 KV、RoPE 融合写入和 Split-KV。

难度 ★★★★参考用时 4 天产出 v0.5A100 即可
承上启下：阶段 10 的 prefill 是算力受限；decode 时每个序列只有 1 个 query，注意力退化为“读完整段 KV 做一次加权求和”，又回到带宽受限。本阶段复用阶段 10 输出的 LSE 合并公式实现 Split-KV，复用阶段 9 的 FP8 知识实现 FP8 KV Cache。

🎯学习目标

  • PagedAttention：KV Cache 按固定大小的块分配，用 block table 把逻辑位置映射到物理块，消除显存碎片
  • GQA：一组 KV 头服务多个 Q 头，同一份 KV 读一次就要给组内所有 Q 头使用
  • Flash-Decoding（Split-KV）：batch 小、上下文长时，沿序列方向切分，最后用 LSE 合并各段结果
  • Decode 前处理的融合：对 Q、K 做 RoPE，并把 K、V 写入分页 Cache，一个 kernel 完成

🛠需实现的功能

  • rope_and_cache：对 Q、K 应用 RoPE（支持 neox 与 GPT-J 两种风格），按 slot_mapping 把 K、V 写入分页 Cache
  • paged_decode_v1：每个 block 负责一个 (序列, Q 头)，warp 内 online softmax，最后跨 warp 合并
  • paged_decode_v2：每个 block 负责一个 (序列, KV 头)，同时计算组内所有 Q 头，KV 只读一次；16 字节向量化读取
  • paged_decode_split + merge_attn_states：Split-KV 及基于 LSE 的合并 kernel
  • 可选：FP8 E4M3 KV Cache（每个头一个 scale），读取时反量化

💡实践要点

  • 先明确并写下 Cache 布局（本教程用 [num_blocks, block_size, num_kv_heads, head_dim]），所有 kernel 和参考实现必须一致
  • 切分数按 “batch × KV 头数” 与 SM 数的比例选择：batch 大时不切，batch=1 长上下文时切到能填满所有 SM
  • 为了能被 CUDA Graph 捕获（阶段 13），序列长度要从显存中的 seq_lens 读取，不能作为 host 端标量传入后决定 grid 大小
  • 合并公式：M = max(m_i)，O = Σ exp(lse_i − M)·O_i / Σ exp(lse_i − M)
  • RoPE 的 cos/sin 表预先计算好；position 从显存读取，同样是为了兼容 CUDA Graph

✅验证方式

  • 参考实现：按 block table 把 KV 收集成连续张量后调用 SDPA；各版本误差小于 1e-2，覆盖 GQA 比例 {1, 4, 8} 和随机打乱的 block table
  • batch 64、上下文 4K 时，paged_decode_v2 的 KV 读取带宽达到峰值的 70% 以上
  • batch 1、上下文 32K 时，Split-KV 比不切分快 3 倍以上
  • rope_and_cache 写入的 Cache 与 PyTorch 参考逐元素一致；若安装了 FlashInfer 或 vLLM，与其 decode kernel 对比性能

// grid = (num_heads, num_seqs)，block = 32 * NUM_WARPS；要求 seq_lens[i] ≥ 1
template <int HEAD_DIM = 128, int BLOCK_SIZE = 16, int NUM_WARPS = 4>
__global__ void paged_decode_v1(
    const half* __restrict__ q,             // [num_seqs, num_heads, HEAD_DIM]
    const half* __restrict__ k_cache,       // [num_blocks, BLOCK_SIZE, num_kv_heads, HEAD_DIM]
    const half* __restrict__ v_cache,       // 同上
    const int* __restrict__ block_tables,   // [num_seqs, max_blocks_per_seq]
    const int* __restrict__ seq_lens,       // [num_seqs]
    half* __restrict__ out,                 // [num_seqs, num_heads, HEAD_DIM]
    int num_heads, int num_kv_heads, int max_blocks_per_seq, float scale) {
  constexpr int VPT = HEAD_DIM / 32;                       // 每个 lane 负责的维度数
  const int head = blockIdx.x, seq = blockIdx.y;
  const int kv_head = head / (num_heads / num_kv_heads);   // GQA 映射
  const int warp = threadIdx.x / 32, lane = threadIdx.x % 32;
  const int len = seq_lens[seq];

  float qv[VPT], acc[VPT] = {};
  const half* qp = q + ((size_t)seq * num_heads + head) * HEAD_DIM + lane * VPT;
  for (int i = 0; i < VPT; ++i) qv[i] = __half2float(qp[i]) * scale;
  float m = -FLT_MAX, l = 0.f;

  for (int t = warp; t < len; t += NUM_WARPS) {            // 每个 warp 轮流处理一个 token
    int pb = block_tables[seq * max_blocks_per_seq + t / BLOCK_SIZE];
    size_t off = (((size_t)pb * BLOCK_SIZE + t % BLOCK_SIZE) * num_kv_heads + kv_head) * HEAD_DIM + lane * VPT;
    float s = 0.f;
    for (int i = 0; i < VPT; ++i) s += qv[i] * __half2float(k_cache[off + i]);
    s = warp_reduce_sum(s);
    float m_new = fmaxf(m, s), alpha = __expf(m - m_new), p = __expf(s - m_new);
    l = l * alpha + p;
    for (int i = 0; i < VPT; ++i) acc[i] = acc[i] * alpha + p * __half2float(v_cache[off + i]);
    m = m_new;
  }

  __shared__ float sm[NUM_WARPS], sl[NUM_WARPS], sacc[NUM_WARPS][HEAD_DIM];
  if (lane == 0) { sm[warp] = m; sl[warp] = l; }
  for (int i = 0; i < VPT; ++i) sacc[warp][lane * VPT + i] = acc[i];
  __syncthreads();
  if (warp == 0) {                                         // 跨 warp 合并 (m, l, acc)
    float M = -FLT_MAX;
    for (int w = 0; w < NUM_WARPS; ++w) M = fmaxf(M, sm[w]);
    float L = 0.f, o[VPT] = {};
    for (int w = 0; w < NUM_WARPS; ++w) {
      float f = __expf(sm[w] - M);
      L += sl[w] * f;
      for (int i = 0; i < VPT; ++i) o[i] += sacc[w][lane * VPT + i] * f;
    }
    half* op = out + ((size_t)seq * num_heads + head) * HEAD_DIM + lane * VPT;
    for (int i = 0; i < VPT; ++i) op[i] = __float2half(o[i] / L);
  }
}

MoE：路由、Token 重排与 Grouped GEMM

实现 MoE 层的完整前向：Top-K 门控 → 按专家重排 → Grouped GEMM → 加权还原。

难度 ★★★★参考用时 4 天产出 v0.6A100 即可

🎯学习目标

  • MoE 前向的数据流与每一步的访存量
  • 负载不均：热门专家的 token 多，冷门专家可能只有几个 token
  • 两种 Grouped GEMM：逐专家循环启动 kernel，与单个 kernel 内按 tile 查表
  • 不依赖 host 同步的设计：专家 token 数在 GPU 上计算，不能拷回 CPU 再决定怎么启动 kernel

🛠需实现的功能

  • topk_softmax：每个 warp 处理一个 token，softmax + Top-K 选择 + 可选的重新归一化
  • moe_align：统计每个专家的 token 数、前缀和，生成按专家排序并填充到 BLOCK_M 倍数的 token 索引

  • 融合 SwiGLU 的 gate/up GEMM epilogue；moe_unpermute：按 Top-K 权重加权求和，还原到原 token 顺序

💡实践要点

  • v2 的 grid 按“最坏情况的 tile 数”启动，多余的 tile 读到空索引后直接返回，这样整个 MoE 层可以被 CUDA Graph 捕获

  • 统计 token 数用原子操作；如需可复现，排序部分用稳定的前缀和方案

// E 为专家数（32 的倍数，≤ 256），K 为每个 token 选中的专家数；每个 warp 处理一个 token
template <int E, int K>
__global__ void topk_softmax(const float* __restrict__ logits, float* __restrict__ topk_w,
                             int* __restrict__ topk_ids, int num_tokens, bool renormalize) {
  constexpr int VPL = E / 32;
  int token = blockIdx.x * (blockDim.x / 32) + threadIdx.x / 32, lane = threadIdx.x % 32;
  if (token >= num_tokens) return;

  float v[VPL], mx = -FLT_MAX;
  #pragma unroll
  for (int i = 0; i < VPL; ++i) { v[i] = logits[(size_t)token * E + i * 32 + lane]; mx = fmaxf(mx, v[i]); }
  mx = warp_reduce_max(mx);
  float sum = 0.f;
  #pragma unroll
  for (int i = 0; i < VPL; ++i) { v[i] = __expf(v[i] - mx); sum += v[i]; }
  sum = warp_reduce_sum(sum);

  float w[K], picked = 0.f;
  int id[K];
  #pragma unroll
  for (int k = 0; k < K; ++k) {
    float best = -1.f; int best_id = E;                    // softmax 概率 ≥ 0，-1 是安全的初值
    #pragma unroll
    for (int i = 0; i < VPL; ++i) if (v[i] > best) { best = v[i]; best_id = i * 32 + lane; }
    #pragma unroll
    for (int o = 16; o > 0; o >>= 1) {                     // warp 内 argmax，并列时取较小编号
      float ob = __shfl_xor_sync(0xffffffff, best, o);
      int oi = __shfl_xor_sync(0xffffffff, best_id, o);
      if (ob > best || (ob == best && oi < best_id)) { best = ob; best_id = oi; }
    }
    w[k] = best / sum; id[k] = best_id; picked += w[k];
    #pragma unroll
    for (int i = 0; i < VPL; ++i) if (i * 32 + lane == best_id) v[i] = -1.f;   // 移出候选
  }
  if (lane == 0) {
    #pragma unroll
    for (int k = 0; k < K; ++k) {
      topk_w[(size_t)token * K + k] = renormalize ? w[k] / picked : w[k];
      topk_ids[(size_t)token * K + k] = id[k];
    }
  }
}

CUDA Graph、Stream 与 PDL

Decode 一步要启动数百个很短的 kernel，CPU 的 launch 开销会成为瓶颈。用 CUDA Graph 一次提交整步，用 PDL 让相邻 kernel 重叠。

难度 ★★★参考用时 3 天产出 v0.7CUDA Graph：A100PDL：H100 / B200 / B300
承上启下：到这里，单个 kernel 已经接近硬件上限，但 decode 一步的总耗时可能仍明显大于各 kernel 耗时之和，多出来的就是 launch 开销和 kernel 之间的空隙。阶段 11、12 中“不依赖 host 端动态信息”的设计，正是为了在这里能被完整捕获成 Graph。

🎯学习目标

  • Launch 开销：每次 kernel 启动需要数微秒的 CPU 时间，与 decode 中单个 kernel 的耗时相当
  • Stream capture 的规则：捕获期间不能同步、不能分配显存、不能根据设备数据在 host 端做分支
  • Graph 中的参数是固定的：输入输出必须使用固定地址的缓冲区，每步原地更新内容
  • 按 batch size 分桶捕获多个 Graph，实际 batch 向上取整到最近的桶
  • PDL（Programmatic Dependent Launch，sm_90+）：下游 kernel 可以提前启动并执行准备工作，在 cudaGridDependencySynchronize() 处等待上游结果

🛠需实现的功能

  • graphs/toy_decoder.cu：用前面阶段的 kernel 拼出 N 层 decoder 的一步 decode，分别以 eager 和 Graph 方式运行
  • batch 分桶 {1, 2, 4, 8, 16, 32, 64, 128}：每个桶捕获一个 Graph，运行时按实际 batch 选择
  • 在 PyTorch 中用 torch.cuda.CUDAGraph 捕获同样的流程，与 C++ 版本对比
  • 在 H100 / B200 / B300 上为 RMSNorm → GEMM 等相邻 kernel 启用 PDL，测量收益
  • 可选：用两个 stream 让互不依赖的操作并行（如 MoE 的共享专家与路由专家）

💡实践要点

  • 捕获前先 warmup：cuBLAS 句柄、workspace、JIT 编译、PyTorch 缓存分配器都需要在捕获前完成初始化
  • “每步都变的量”（序列长度、位置、block table）都放在显存缓冲区中由 kernel 读取，不要作为 kernel 参数传值
  • PyTorch 中多个 Graph 可以共享一个显存池（pool= 参数），避免显存翻倍
  • 参数变化不大时可以用 cudaGraphExecUpdate 更新已实例化的 Graph，比重新实例化快得多
  • PDL 中，上游 kernel 可以调用 cudaTriggerProgrammaticLaunchCompletion() 提前放行下游；下游在读取上游输出之前必须调用 cudaGridDependencySynchronize()

✅验证方式

  • Graph 版本的输出与 eager 版本逐位一致
  • batch 1 时，每步 decode 延迟明显下降（报告具体数字），Nsight Systems 中 kernel 之间的空隙基本消失
  • CPU 侧每步提交时间从“与 kernel 数成正比”变为常数
  • （H100+）启用 PDL 后，相邻 kernel 在时间线上出现重叠，端到端有可测量的收益

📦阶段性产出

  • graphs/、docs/s13_graph.md（eager / Graph / Graph + PDL 三者的 Nsight Systems 截图与延迟对比）；git tag v0.7

一、GPU 执行模型：先认识这台"工厂"

1.1 为什么 CPU 的思维在 GPU 上行不通

CPU 是为低延迟设计的：少数几个强核心，大缓存、乱序执行、分支预测，目标是让单个线程尽可能快。GPU 恰好相反，是为高吞吐设计的：成千上万个简单核心，目标是让海量线程的总产出最大。

一个直观的对比：

维度CPUGPU
设计目标单线程低延迟总吞吐量
核心数几个～几十个数千个（以 SM 为组织单位）
单核能力强（乱序、高主频）弱（顺序、低主频）
延迟对策大缓存 + 预取多线程切换掩盖延迟
适合的任务分支密集、串行逻辑大规模数据并行

理解了这一点，后面所有概念（warp、SIMT、调度器）都是围绕"如何高效喂养这么多核心"展开的。

1.2 SM：GPU 的"车间"

GPU 内部的基本计算单位是 SM（Streaming Multiprocessor，流式多处理器）。可以把 GPU 想成一家工厂，SM 就是其中的一个个车间：

  • 一块 GPU 有几十到一百多个 SM（例如 A100 有 108 个 SM）；
  • 每个 SM 内部包含：数十个 CUDA core（做基本算术逻辑）、张量核心（做矩阵乘等 AI 运算）、一大坨寄存器堆、一块共享内存/L1 缓存、若干 warp 调度器以及访存和特殊函数单元；
  • SM 是线程的"宿舍"：一个 block 的所有线程会被完整地安排到同一个 SM 上执行，共享该 SM 的寄存器和共享内存。

💡 关键认知：SM 内的寄存器与共享内存是分给驻留线程瓜分的稀缺资源。一个线程要的寄存器越多，能同时住进 SM 的线程就越少——这是后续优化"占用率（occupancy）“的根源。

1.3 线程层级：thread → block → grid

CUDA 用三层结构组织线程：

  • thread：最小单位，对应一个 kernel 函数的一次执行实例；
  • block：若干线程组成一个块，块内线程可通过共享内存协作、通过 __syncthreads() 同步；
  • grid：所有 block 的集合，一次 kernel 启动就是一个 grid。

一个最小示例——向量加法：

// kernel：每个线程负责一个元素
__global__ void vec_add(const float* a, const float* b, float* c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) c[i] = a[i] + b[i];      // 边界检查不可少
}

// 启动：256 个线程一个 block，共 ceil(n/256) 个 block
int threads = 256;
int blocks  = (n + threads - 1) / threads;
vec_add<<<blocks, threads>>>(d_a, d_b, d_c, n);

全局线程编号 i = blockIdx.x * blockDim.x + threadIdx.x 是 CUDA 最常见的模式：每个线程靠它"找到自己的活儿”。调度器会把这些 block 分发到各个 SM 上——block 之间彼此独立，这也是 GPU 能横向扩展到成百上千个 SM 的原因。

1.4 Warp：真正被调度与执行的单位

虽然我们按 thread 写代码，但硬件根本不以单线程为单位执行。线程真正成形的单位是 warp：连续 32 个线程。

规则很简单：

  • 一个 block 内，线程按 threadIdx.x 顺序每 32 个切成一个 warp；
  • 硬件上真正取指、译码、发射的对象是 warp 整体——32 个线程共享一个程序计数器（PC），锁步（lockstep）执行同一条指令。

一个简单的推算示例：blockDim = 100 的 block 会被切成 ⌈100/32⌉ = 4 个 warp：

Warp覆盖的 threadIdx有效线程数
warp 00–3132（满员）
warp 132–6332（满员）
warp 264–9532（满员）
warp 396–994（其余 28 个槽位空转）

💡 这就是 CUDA 代码习惯把 blockDim 取 128 / 256 这类 32 的倍数的原因：不满员的 warp（尾块，tail warp）照样占用一个执行槽位，但只有部分线程在干活，相当于白白浪费吞吐。把数据规模对齐到 32 的倍数（或让尾块尽可能少）是零成本优化。

1.5 Warp 调度器：延迟隐藏的秘密

warp 执行指令时会经常"卡住"——一条全局内存访问要几百个时钟周期才返回。如果是 CPU 的思路，就得靠缓存或预取来消灭等待；GPU 的思路则粗暴得多：等就等，我先去执行别的 warp。

每个 SM 里驻留着大量 warp（可能几十个），由 warp 调度器统一管理：

每个周期：
  从所有驻留 warp 中挑一个 "就绪（ready）" 的
  → 向它的 32 个线程发射一条指令
  → 若该 warp 需要等待（访存未返回等），标记为阻塞
  → 立刻切换到下一个就绪 warp

打个比方：一位厨师同时照看 8 口锅。任何一口菜在"焖煮等待"时，他并不闲着，而是去翻炒下一口锅。单锅出菜未必快，但 8 口锅的总产出远高于盯着一口锅等的厨师。

由此引出一个贯穿后续优化始终的指标——占用率（occupancy）：SM 上实际驻留的 warp 数 / 该 SM 最大可驻留 warp 数。驻留的 warp 越多，调度器手里可供切换的"活儿"越多，越容易把访存延迟藏起来。而驻留 warp 数受 block 尺寸、每线程寄存器用量、共享内存用量共同限制——这正是 1.2 节"稀缺资源"的回响。

1.6 SIMT：单指令多线程

warp 的锁步执行有个正式名字：SIMT（Single Instruction, Multiple Threads，单指令多线程）。它与 CPU 世界常见的 SIMD 有微妙但重要的区别：

SIMD（如 AVX 指令）SIMT（CUDA）
编程模型显式使用向量指令/内建函数每个线程写标量代码，硬件自动并行
线程状态一个向量寄存器代表 8/16 个 lane每线程有独立寄存器组与数据
分支必须全程锁步，无分支能力允许分支，代价是"分歧"

SIMT 最著名的坑是分支分歧（warp divergence）。warp 内 32 个线程只有一个 PC，当线程走向不同路径时，硬件只能把两条路径串行执行：

// 反例：warp 内线程走向不同分支 → 两条路径串行执行
__global__ void kernel(float* x, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i % 2 == 0)      x[i] = x[i] * 2.0f;   // 路径 A
    else                 x[i] = x[i] + 1.0f;   // 路径 B
    // warp 0 的 32 个线程中 16 个走 A、16 个走 B
    // → 硬件先执行 A（16 个线程干活，16 个空转）
    //   再执行 B（另外 16 个干活，16 个空转）
    // 有效利用率 ~50%
}

改善思路是让同一个 warp 内的线程尽量走同一条路径，例如按 warp 对齐来切分数据（if (warp_id % 2 == 0) 代替 if (i % 2 == 0)），或把不同分支的数据拆到不同 block。

📌 小结：SM 是车间，warp 是干活的班组（32 人锁步），调度器靠在多个班组间快速轮换来掩盖延迟，SIMT 则是班组的工作纪律（一条指令全员执行，分歧要付代价）。

二、Compute Capability 与编译体系

2.1 Compute Capability：GPU 的"代际编号"

Compute Capability（CC，计算能力）是 NVIDIA 给每代 GPU 架构的编号，格式为 major.minor：

  • major 对应大架构代际：8 = Ampere（A100），9 = Hopper（H100），10 = Blackwell（B200/B300）；
  • minor 标记同代内的型号差异，某些特性以 a 后缀的架构目标区分（见 2.4）。

CC 之所以重要，是因为它同时决定两件事：

  1. 硬件特性：能不能用 TMA（张量内存加速器）、wgmma/tcgen05 张量核心指令、多大的共享内存 opt-in 上限等；
  2. 编译目标：SASS 机器码与架构一一对应，为 CC 8.0 编译的机器码不能在 CC 9.0 上跑。
GPU架构Compute Capability最低 CUDA Toolkit
A100Ampere8.011.0
H100Hopper9.011.8（建议 12.x）
B200Blackwell10.012.8
B300Blackwell10.312.9

⚠️ 最后一列是常见踩坑点：新卡到手却用旧 Toolkit，编译阶段就无目标可编；PyTorch 同理要选对应的 wheel（如 cu128 或更新）。

2.2 PTX 与 SASS：中间表示 vs 机器码

理解编译体系的第一步，是分清两种"代码形态"：

  • PTX（Parallel Thread Execution）：CUDA 的虚拟架构中间表示，类似传统编译器里的 LLVM IR。它面向"抽象的 CUDA 虚拟机"而非具体硬件，指令集稳定、可读（人能看懂）；
  • SASS（Streaming ASSembler）：面向具体某代架构的真实机器码。每代 GPU 的 SASS 都不同，A100 的 SASS 放到 H100 上就是一堆无法解码的字节。

nvcc 的编译流水线：

.cu 源码
  │  cicc（前端编译）
  ▼
 PTX（虚拟中间表示）
  │  ptxas（针对目标架构汇编）
  ▼
 SASS（某代架构的机器码）

两者的核心差异可以浓缩成一张表：

PTXSASS
定位中间表示（IR）真实机器码
面向抽象虚拟架构具体某代 GPU
跨代兼容✅ 可前向兼容（靠 JIT）❌ 只能本代运行
性能需运行时编译，可能有首次启动开销直接执行，最快

2.3 fatbinary：一个文件装多份代码

一个现实问题：发布的程序要在 A100、H100、B200 上都能跑，SASS 又不跨代，难道要发三个二进制？

答案就是 fatbinary（胖二进制）：nvcc 允许把多份编译产物（若干代的 SASS + 一份 PTX）全部嵌入同一个可执行文件。运行时驱动根据实际 GPU 挑选：

  • 有本架构的 SASS → 直接加载，最快；
  • 只有覆盖该卡的 PTX → 驱动在运行时 JIT 编译成 SASS（首次启动有编译开销，之后有缓存）；
  • 两者都没有 → 报错 no kernel image is available for execution on the device。

你可以用 cuobjdump 亲自验证 fatbinary 里装了什么：

cuobjdump -sass app        # 列出内嵌的各架构 SASS

2.4 -gencode：决定 fatbinary 里装什么

-gencode 就是控制"往胖二进制里塞哪些产物"的编译选项，语法：

-gencode arch=compute_XX,code=[sm_XX, compute_XX]
                        │           │        └─ 嵌入一份 PTX（供未来卡 JIT）
                        │           └─ 嵌入 XX 架构的 SASS
                        └─ 以 XX 虚拟架构为编译目标

来自实践的多架构发布命令：

# 同时为 A100 / H100 / B200 / B300 生成代码
nvcc -O3 -std=c++17 -lineinfo \
  -gencode arch=compute_80,code=sm_80 \
  -gencode arch=compute_90a,code=sm_90a \
  -gencode arch=compute_100a,code=sm_100a \
  -gencode arch=compute_103a,code=sm_103a \
  -o app app.cu

几个必须知道的细节：

  • code= 里写什么决定了塞什么：写 sm_80 只嵌入 SASS；写 [sm_80,compute_80] 则 SASS 与 PTX 各嵌一份。多架构发布的稳妥做法是同时嵌入 SASS 和 PTX——SASS 保证已支持架构的最优执行，PTX 兜底保证未来的新卡能 JIT 运行；
  • a 后缀（如 sm_90a、sm_100a）：使用该代架构专属指令（如 Hopper 的 wgmma）的目标。这类目标不向前兼容，连 JIT 都救不了，必须精确匹配代际；CUDA 12.9 起提供了 f 后缀的"同族"目标以缓解这一问题；
  • -lineinfo 请始终加上：它把源码行号信息嵌入二进制，让 Nsight Compute 能把性能指标对应到源码行，且几乎不影响运行性能。代价为零，收益巨大。

2.5 JIT：PTX 的"保底机制"

当 fatbinary 中没有当前 GPU 的 SASS、但有"辈分更低"的 PTX 时，CUDA 驱动会在运行时把 PTX 编译为本机 SASS，即 JIT（Just-In-Time）编译。

  • 触发场景：程序发布后 NVIDIA 又出了新架构 GPU（例如二进制带 PTX，老程序跑上了新卡）；
  • 代价：首次运行某个 kernel 时有明显编译延迟（结果会被驱动缓存，之后不再编译）；
  • 边界：PTX 只前向兼容（旧 PTX → 新卡），a 后缀目标除外；反向（新 PTX → 旧卡）不存在。

📌 小结：CC 是代际编号，SASS 是每代的方言，PTX 是通用语，fatbinary 是"多语种合订本"，-gencode 决定合订本里收录哪几篇，JIT 是驱动现场的口译员。

三、Driver / CUDA Toolkit / PyTorch 的版本兼容

初学者最容易混乱的一件事：系统里到处都是"CUDA 版本"，它们根本不是同一个东西。先把三个角色拆开。

3.1 三个角色分别是什么

角色是什么在哪里看版本
Driver（驱动）内核态 + 用户态驱动，管理 GPU 硬件、执行 JIT 编译nvidia-smi 右上角
CUDA Toolkit开发工具包：nvcc 编译器、头文件、库、Nsight 工具nvcc --version
PyTorch 的 CUDA 版本pip/conda 安装的 PyTorch wheel 自带的 CUDA runtime 与 kernel 库torch.version.cuda

关键点：PyTorch 不依赖你系统里装的 Toolkit。官方 wheel 把所需的 CUDA 运行时和为各架构预编译好的 kernel（一份巨大的 fatbinary）全部打包在包内。系统 Toolkit 只有在你本地编译 CUDA 扩展（如 torch.utils.cpp_extension）时才会被用到。

3.2 三条兼容规则

规则 1：Driver 向后兼容旧 Toolkit。
CUDA 驱动保证对旧版本 Toolkit 编译出的程序兼容。实践准则：驱动版本 ≥ Toolkit 要求的最低版本即可。注意 nvidia-smi 右上角显示的 CUDA Version: 12.x 指的是该驱动最高支持的 CUDA 版本，不是系统已安装的版本——这是最常见的误读。

规则 2：Toolkit 必须支持你的 GPU 架构。
对应 2.1 节的表格：B200 需要 CUDA 12.8+，B300 需要 CUDA 12.9+。Toolkit 太旧，nvcc 根本没有该 CC 的编译目标。

规则 3：PyTorch 只看 wheel。
PyTorch 能否用上你的 GPU，取决于 wheel 标签（如 cu126、cu128）里的 kernel 是否覆盖你的架构。装 PyTorch 前查清楚：新卡（B200 及以后）必须选 cu128 或更新的 wheel。

3.3 环境检查清单

三条命令把三方版本拉齐对账：

# ① 驱动 + 驱动支持的最高 CUDA 版本 + GPU 型号
nvidia-smi

# ② 本地 CUDA Toolkit（nvcc）版本
nvcc --version

# ③ PyTorch 的 CUDA 版本，以及它看到的 GPU 架构
python -c "import torch; print(torch.version.cuda, torch.cuda.get_device_capability())"

最后一条的输出应与本机实际 CC 一致（A100 → (8, 0)，H100 → (9, 0)）。把这三项写成脚本（如 scripts/env_check.sh），是每个新环境的第一个动作。

3.4 经典报错：no kernel image is available

跑到一块 GPU 上报：

CUDA error: no kernel image is available for execution on the device

含义：当前程序的 fatbinary 里没有任何能在本卡上执行的代码。按频次排查两种成因：

  1. 编译目标不含当前架构：二进制只嵌了旧架构 SASS、没带 PTX（忘了 code=[sm_XX,compute_XX] 里的 PTX），在新卡上既没有 SASS 也没有可 JIT 的 PTX；
  2. PyTorch 的 CUDA 版本太旧：如 B200 上装了 cu118/cu126 的 wheel——wheel 里预编译的 kernel 覆盖不到新架构。换装 cu128 或更新的 wheel。

📌 小结：驱动管"能不能跑"，Toolkit 管"能不能编"，PyTorch wheel 管"自带 kernel 覆盖哪些卡"。三者各查各的版本，别混为一谈。

四、常用工具：正确性与性能分析的完整链路

4.1 nvcc：CUDA C++ 编译器

nvcc 是 CUDA 的编译驱动，负责把 .cu 中的 host 代码与 device 代码分离编译并链接。日常最小命令集：

# 单架构快速编译
nvcc -O2 -lineinfo -o app app.cu

# 查看本机 nvcc 支持的架构目标
nvcc --list-gpu-arch

# 多架构发布（见 2.4 节完整示例）
nvcc -O3 -lineinfo -gencode arch=compute_80,code=[sm_80,compute_80] ...

习惯建议：日常开发用一个 -gencode 目标加快编译；发布构建再展开成多架构 + PTX 兜底。

4.2 compute-sanitizer：正确性检查的守门员

性能优化之前必须先保证正确。compute-sanitizer 是一组运行时检查器，能在错误发生的第一现场报出详细信息：

子工具检查内容
memcheck（默认）越界访问、未对齐访问、use-after-free
racecheck共享内存的数据竞争
synccheck同步原语的错误使用
initcheck未初始化内存的读取

用法就是在命令前加前缀，代价是运行明显变慢：

compute-sanitizer ./app
compute-sanitizer --tool racecheck ./app

一个值得亲手做一次的实验：写一个故意越界的小 kernel（比如去掉 1.3 节 vec_add 里的边界检查），用 compute-sanitizer 跑一遍，亲眼看到它报出越界的地址、线程编号和源码行。这一课的价值在于：以后遇到"结果偶发不对"，你会条件反射地先跑 sanitizer。

4.3 Nsight Systems：全局时间线分析

nsys 回答的是宏观问题：“我的程序时间都花在哪了？”

它记录整个程序的时间线：每个 kernel 的起止、内存拷贝（H2D/D2H）、CUDA API 调用、CPU 侧的活动，然后以瀑布图呈现。典型用途：

  • 找出热点 kernel：哪个 kernel 占了大头；
  • 发现串行化：数据拷贝与计算是否可以重叠（CUDA stream）；
  • 识别时间线上的 gap：kernel 之间空转、等待拷贝、主机端逻辑拖后腿。
nsys profile -o report ./app     # 采集
nsys stats report.nsys-rep       # 输出统计摘要（top kernel 等）
nsys-ui report.nsys-rep          # 图形界面看时间线

核心方法论：先用 Nsight Systems 定位瓶颈在哪个环节。如果瓶颈根本不在 kernel 里（比如在数据搬运），拿着 Nsight Compute 瞎优化 kernel 是白费劲。

4.4 Nsight Compute：单 kernel 深度剖析

ncu 回答的是微观问题：“这一个 kernel 为什么慢？”

它对单个 kernel 做深度采样，报告硬件计数器级指标：

  • Speed of Light（SOL）：计算吞吐与访存吞吐各离理论上限多远——直接告诉你 kernel 是算力受限还是带宽受限；
  • 占用率（Occupancy）：实际驻留 warp 与上限的比值（呼应 1.5 节）；
  • Warp State / Stall 原因：warp 都在等什么（等内存？等屏障？等分支？）；
  • 源码级归因：配合 -lineinfo，把每个指标对应到具体源码行。
ncu --set full -o kernel_report ./app     # 全指标剖析
ncu --set basic ./app                     # 快速概览

注意事项：剖析会大幅拖慢 kernel 运行，且 --set full 每次只剖析有限个 kernel 实例——先在 nsys 里锁定目标，再针对性 ncu。

4.5 工具选择：一条固定的分析流水线

四个工具按此顺序使用，形成完整闭环：

① nvcc -lineinfo 编译
        ▼
② compute-sanitizer —— 保证正确（错就先修错）
        ▼
③ Nsight Systems —— 时间线定位：瓶颈是哪个 kernel / 环节
        ▼
④ Nsight Compute —— 对热点 kernel 深剖：为什么慢
        ▼
回到 ①，改代码再循环

五、动手实践：把知识落地

学完概念，最后一步是量化本机硬件。两份参考实现：

5.1 device_info.cu：摸清手上 GPU 的家底

// tools/device_info.cu —— nvcc -O2 -o device_info device_info.cu
#include <cstdio>
#include <cuda_runtime.h>

int main() {
  int dev = 0;
  cudaDeviceProp p;
  cudaGetDeviceProperties(&p, dev);
  int mem_clk_khz, bus_bits, smem_optin;
  cudaDeviceGetAttribute(&mem_clk_khz, cudaDevAttrMemoryClockRate, dev);
  cudaDeviceGetAttribute(&bus_bits, cudaDevAttrGlobalMemoryBusWidth, dev);
  cudaDeviceGetAttribute(&smem_optin, cudaDevAttrMaxSharedMemoryPerBlockOptin, dev);

  printf("GPU %s | CC %d.%d | SMs %d\n", p.name, p.major, p.minor, p.multiProcessorCount);
  printf("L2 %.1f MB | smem/SM %zu KB | smem/block(opt-in) %d KB | regs/SM %d\n",
         p.l2CacheSize / 1048576.0, p.sharedMemPerMultiprocessor / 1024,
         smem_optin / 1024, p.regsPerMultiprocessor);
  printf("Theoretical DRAM BW: %.0f GB/s\n", 2.0 * mem_clk_khz * 1e3 * (bus_bits / 8) / 1e9);
}

三个看点：

  • 理论显存带宽 = 2 × 显存时钟 × 位宽 / 8（DDR 每周期传两次、位宽按 bit 换算成 byte）。与官方 datasheet 对比，误差应在 5% 以内——这个数字是后续一切访存优化的"天花板"；
  • 用 cudaDeviceGetAttribute 逐项查询，而不是 cudaDeviceProp 的字段：CUDA 13 已移除 memoryClockRate 等字段，attribute 接口是统一且面向未来的做法；
  • 输出的 SM 数、共享内存上限、寄存器数，就是 1.2 节"车间资源清单"在你机器上的具体数值。

5.2 bench/util.py：可信的计时框架

# bench/util.py —— 所有基准共用的计时工具
import torch

def bench(fn, warmup=20, iters=100):
    for _ in range(warmup):
        fn()                                # 预热：触发 JIT、建缓存、拉高频
    torch.cuda.synchronize()                # 确保预热全部落地
    st = torch.cuda.Event(enable_timing=True)
    ed = torch.cuda.Event(enable_timing=True)
    st.record()                             # 在 GPU 时间线上打点
    for _ in range(iters):
        fn()
    ed.record()
    torch.cuda.synchronize()
    return st.elapsed_time(ed) / iters      # 毫秒

def report(name, ms, bytes_moved=0, flops=0):
    gbps = bytes_moved / ms / 1e6 if bytes_moved else 0.0
    tflops = flops / ms / 1e9 if flops else 0.0
    print(f"{name:<32}{ms * 1e3:10.1f} us {gbps:9.0f} GB/s {tflops:8.1f} TFLOPS")

两个必须理解的设计决策：

  • 为什么用 CUDA Event 而不是 time.time()：CPU 发出 kernel 启动命令后立即返回，GPU 还在异步执行。用 CPU 侧时钟计时，量到的是"提交命令"的时间而非"执行"的时间。CUDA Event 在 GPU 时间线上打点，才是 kernel 的真实耗时；
  • 为什么先 warmup：首次运行触发 JIT 编译（2.5 节）、缓存冷启动、时钟频率未拉满，这些一次性开销不能混进稳态测量。

CUDA 入门教程（四）：归约、Warp 原语与 Softmax

系列：CUDA 与 GPU 编程入门 · 第 3 阶段 参考用时：3 天 ｜ 难度：★★ ｜ 前置：教程（三）矩阵转置 ｜ 硬件：A100 即可

🎯 学习目标

归约（reduction）是推理算子中出现最多的计算模式：Softmax、LayerNorm、Attention、Top-K 采样都离不开它。教程（三）处理的是"搬运"，本章第一次处理线程间协作。学完你应当能够：

  1. 掌握树形归约：理解朴素归约的 warp divergence 代价，解释为什么最后 32 个元素要交给 warp shuffle 做；
  2. 掌握 warp shuffle 原语：准确说出 __shfl_xor_sync / __shfl_down_sync 的语义和 mask 参数的作用，写出可复用的 warp_reduce_sum/max 与 block_reduce_sum/max；
  3. 掌握数值稳定性：推导 safe softmax（减最大值）为什么防溢出，理解 online softmax 如何一趟同时得到最大值与归一化分母，把读取次数从 3 次减到 2 次；
  4. 掌握原子操作与两趟归约的取舍：在性能、确定性与可复现性之间做工程决策。

承上启下：本章写进 common.cuh 的 warp_reduce_sum/max 和 block_reduce，后续几乎每个阶段都会复用（归一化、GEMV、decode attention）；online softmax 是阶段 10 FlashAttention 的数学核心。

一、归约：把 N 个数变成 1 个数

问题设定：长度为 N 的数组求和（或求最大值），N 从几千到数亿。它是所有"统计量"计算的骨架：

softmax:   每行需要 max（稳数值） + sum（归一化分母）     → 两种归约
LayerNorm: 每行需要 mean + var                              → 两种归约
Attention: 每行分数需要加权求和                              → 归约
Top-K 采样: logits 上反复筛极值                              → 归约的变体

归约的难点不在算术（就是加法），而在协作方式：每个线程手里有一份部分和，怎么高效地合并成全局结果？合并的过程天然是串行依赖的树，而 GPU 擅长的是并行——矛盾如何化解，正是本章的主线。

二、树形归约与 warp divergence

2.1 朴素做法及其两宗罪

最直觉的写法：每个线程算一段部分和，然后让线程 0 一个个加起来：

// 反面教材：串行合并
__shared__ float partial[256];
partial[threadIdx.x] = my_partial_sum;
__syncthreads();
if (threadId.x == 0) {                          // ← 罪一：255 个线程围观
    float s = 0;
    for (int i = 0; i < 256; ++i) s += partial[i];
    result = s;                                  // 256 次串行 smem 读
}

改进成树形，但用"步长翻倍 + 取模判断"（Mark Harris 经典七步优化的起点）：

// 仍有问题的树形：顺序配对
for (int s = 1; s < blockDim.x; s *= 2) {
    if (threadIdx.x % (2 * s) == 0)              // ← 罪二：分支分歧
        partial[tid] += partial[tid + s];
    __syncthreads();
}

罪一（串行）：% (2s) == 0 让活跃线程逐层减半——第 6 层只剩 4 个线程干活，其余 252 个全在围观，还占着 warp 槽位。 罪二（divergence）：活跃线程在 warp 内交错分布（不是整 warp 退出），每个 warp 都要同时执行"加"和"不加"两条路径——正是教程（一）1.6 节的 warp 分支分歧，SIMT 为分歧付出双倍指令。

2.2 树形归约的正确姿势

把"取模配对"改成相邻配对（前半加后半），warp 整段退出而非交错：

// 交错配对树形：无发散的正确版本（示例为 8 元素）
__shared__ float sdata[8];
sdata[threadIdx.x] = x[threadIdx.x];  __syncthreads();
for (int s = 4; s > 0; s >>= 1) {
    if (threadIdx.x < s)
        sdata[tid] += sdata[tid + s];
    __syncthreads();
}
// 结果在 sdata[0]

8 个元素的树（每层活跃线程减半，但前半连续、warp 整体退出）：

层 0 (s=4):  t0 t1 t2 t3 加各自 +4 邻居      [a0+a4] [a1+a5] [a2+a6] [a3+a7]  _  _  _  _
层 1 (s=2):  t0 t1 继续                      [..+a2+6] [..+a3+7]              _  _  _  _  _  _
层 2 (s=1):  t0 收官                         [总和]                           ...
     深度 = log2(N)，每层一次 __syncthreads

到 N=8 时一切安好；但把 N 放大到 1024，注意观察最后几层：活跃线程只剩 32、16、8……全部位于 warp 0。此刻一个关键事实浮出水面——

2.3 为什么最后 32 个元素交给 warp shuffle（学习目标 ① 的核心）

当树形归约进行到只剩 32 个元素时，剩下的 32 个活跃线程恰好构成一个 warp。而 warp 内的"树形"根本不需要 Shared Memory 和 __syncthreads()：

  1. warp 天然锁步（SIMT）：32 个 lane 执行同一条指令，不存在"谁先谁后"的竞争，无需任何屏障；
  2. shuffle 直接在寄存器间交换数据：lane 5 的寄存器值可以一步递给 lane 1，不经过 Shared Memory——没有 smem 写、没有 bank、没有 __syncthreads，也就没有 block 树每层一次的屏障开销；
  3. 蝶形（XOR）配对零发散：见下节的配对方式——每一步 32 个 lane 全员参与，没有围观者，SIMT 完全满载。

对比一下同一棵"剩 32 元素的树"的两种走法：

Shared Memory 树warp shuffle 树
数据通路寄存器 → smem → 寄存器寄存器 ↔ 寄存器（硬件直连）
同步每层一次 __syncthreads()不需要（warp 锁步）
活跃线程逐层减半（16→8→4…）32 路全满载（蝶形对称）
5 层总开销5 次 smem 往返 + 5 次屏障5 条 shuffle 指令

这就是 CUDA 归约的标准终局：block 树只砍到 warp 边界，最后 32 个元素用 shuffle 蝶形一步收官。

三、Warp Shuffle 原语：__shfl_*_sync 的语义与 mask（学习目标 ②）

3.1 两个原语：down 与 xor

shuffle 指令让同一 warp 内的 lane 交换寄存器值，一条指令完成、不走内存：

float __shfl_down_sync(unsigned mask, float v, int offset);   // lane i ← lane i+offset
float __shfl_xor_sync (unsigned mask, float v, int laneMask); // lane i ← lane i^laneMask

以 8 个 lane（编号 0–7）、值 a0..a7 为例，两种配对方向：

__shfl_down_sync(mask, v, 4)：                 __shfl_xor_sync(mask, v, 4)：
lane:  0   1   2   3   4   5   6   7           lane:  0   1   2   3   4   5   6   7
收到: a4  a5  a6  a7  a4  a5  a6  a7           收到: a4  a5  a6  a7  a0  a1  a2  a3
      ↑ 向下取数，高 lane 越界取自身                ↑ 对称互换（i 与 i^4 互为目的地）

再下一步 o=2:                                   o=2:
收到: a2  a3  a2  a3 ...                        收到: a2  a3  a0  a1  a6  a7  a4  a5
最后 o=1:                                       o=1:
lane0 拿到总和 ✔（仅 lane 0 有用）              lane0 拿到总和 ✔（所有 lane 都有总和）

关键区别：

  • down 是"单向流"：数据只往低 lane 走，做完只有 lane 0 持有结果——适合"归约完只有主线程有用"的场景；
  • xor 是"蝶形互换"：每步双方互换，做完 32 个 lane 全都持有结果（广播免费）——适合后续所有线程都要用归约值的情况（softmax 每个线程都要除以 sum）。此外它每步全员干活、零 divergence，是性能首选。

3.2 mask 参数：给谁看的？

_sync 后缀和 mask 参数解决一个真实风险：warp 内可能发生分支分歧（教程一 1.6 节）。如果部分 lane 已经 return 或走了别的分支，而 shuffle 却试图从"不存在的 lane"取数，行为就是未定义的。

规则：

  • mask 是一个 32 位位掩码，第 i 位为 1 表示 lane i 参与这次 shuffle；
  • mask 里列出的所有线程，必须都实际执行到这条 shuffle 指令（硬件靠 mask 做锁步对齐）；
  • 全员参与就写 0xffffffff；部分参与要精确计算，如前 nw 个 lane 参与时 mask = (1u << nw) - 1。
// 常见坑：条件 return 后 shuffle
if (row >= rows) return;                 // 部分 lane 退出
... __shfl_xor_sync(0xffffffff, v, 1);   // ✘ mask 说全员参与，实际只有部分 lane 到达 → 未定义行为

// 正确姿势 A：先归约后退出（把 return 放在 shuffle 之后）
// 正确姿势 B：让退出条件以 warp 为单位（整 warp 一起 return）
if (row >= rows) { if (__all_sync(0xffffffff, true)) return; }  // 整 warp 同进退

还有一种"伪装参与"的经典技巧——全员执行、惰性填零，后面 block_reduce_sum 里 lane < nw ? partial[lane] : 0.f 就是它：与其让部分 lane 退出引发分歧，不如让全 warp 都跑、多余 lane 贡献一个 0（加法单位元）。

3.3 warp_reduce_sum / max：本章的第一件传家宝

// common.cuh：warp 内蝶形归约，结果广播到所有 lane
__device__ __forceinline__ float warp_reduce_sum(float v) {
  #pragma unroll
  for (int o = 16; o > 0; o >>= 1) v += __shfl_xor_sync(0xffffffff, v, o);
  return v;
}
__device__ __forceinline__ float warp_reduce_max(float v) {
  #pragma unroll
  for (int o = 16; o > 0; o >>= 1) v = fmaxf(v, __shfl_xor_sync(0xffffffff, v, o));
  return v;
}

32 lane 的蝶形全程（每轮 lane i 与 lane i^o 互换并合并，5 轮后全员持和）：

初始:  [v0] [v1] [v2] ... [v31]                    每 lane 持自己的值
o=16:  lane i ←—互换—→ lane i^16；合并后 lane 0..15 持 (v0+v16) 型的两两和
o=8:   lane i ↔ i^8；lane 0..7 持 4 元素和
o=4:   → lane 0..3 持 8 元素和
o=2:   → lane 0..1 持 16 元素和
o=1:   → **所有 32 个 lane 都持 32 元素总和** ✔

两个工程细节：#pragma unroll 让 5 轮循环在编译期展开（offset 是编译期常量，shuffle 指令可直排）；__forceinline 保证内联进调用方，不产生真实函数调用开销。

3.4 block_reduce_sum：warp 归约 + 二级汇总 + 广播

block 有多个 warp，标准三段式：

// block 归约：先 warp 内，再由 warp 0 归约各 warp 的部分和，最后广播给全部线程
__device__ float block_reduce_sum(float v) {
  __shared__ float partial[32];
  __shared__ float total;
  int lane = threadIdx.x & 31, wid = threadIdx.x >> 5;
  v = warp_reduce_sum(v);                 // ① 每 warp 蝶形归约（寄存器内，5 条指令）
  if (lane == 0) partial[wid] = v;        // ② 每 warp 的结果由 lane 0 写入 smem
  __syncthreads();                        //    ← 屏障 1：等所有 partial 落盘
  if (wid == 0) {
    int nw = (blockDim.x + 31) >> 5;
    v = warp_reduce_sum(lane < nw ? partial[lane] : 0.f);  // ③ warp 0 收拢（惰性填零防分歧）
    if (lane == 0) total = v;
  }
  __syncthreads();                        //    ← 屏障 2：等 total 落盘
  return total;                           // ④ 广播给全 block
}

流程图（block = 8 warp 示例）：

warp0 ─蝶形→ w0 ┐
warp1 ─蝶形→ w1 ┤                         ┌→ total ──┐
  ⋮             ├─ smem partial[0..7] ──→ warp0 收拢 ─┤ __syncthreads → 全员读 total
warp7 ─蝶形→ w7 ┘   (lane0 写入)             (填零到32) └───────────┘

⚠️ 源页面明确警告的陷阱：同一个 kernel 里两次调用 block_reduce 时，两次都会使用同一块 partial 共享内存。第一次调用结尾的 __syncthreads() 并不能保护第二次调用开头的写入——某个快线程可能已经冲进第二轮 partial[wid] = v，覆盖了慢线程还没读走的旧值。解法：在两次调用之间显式补一次 __syncthreads()（Softmax 恰好要连做 max 和 sum 两个归约，此坑必踩）。

四、数值稳定性与 Softmax

4.1 softmax 为什么会"炸"

softmax 定义：y_i = e^{x_i} / Σ_j e^{x_j}。它有个致命的数值问题——指数爆炸：

x_i = 1000 → e^1000 ≈ 10^434 → float 上限 3.4×10^38 → Inf
Inf / Inf = NaN → 整行报废

训练/推理中的 logits 上千很常见（尤其大 attention score），必须处理。

4.2 safe softmax：减去最大值

数学恒等式：给分子分母同乘 e^{-m}，值不变：

y_i = e^{x_i} / Σ e^{x_j} = e^{x_i - m} / Σ e^{x_j - m}      （m 为任意常数）
取 m = max_j(x_j) → 所有指数 ≤ 0 → 最大项 e^0 = 1，永不溢出 ✔

代价是先要知道 max——于是朴素的三趟实现：

第 1 趟：读 x → block/warp 归约 max
第 2 趟：读 x → Σ e^{x_i - m} 归约 sum
第 3 趟：读 x → 写 y_i = e^{x_i-m} / sum
─────────
全局内存读取 3 次（带宽受限算子，AI ≈ 0，读几次就直接决定几倍耗时）

4.3 online softmax：一趟同时拿到 m 和 d（学习目标 ③ 的核心）

三趟的浪费在于"必须先知道全局 max 才能安全累加"。Online softmax（Milakov & Gimelshein, 2018）的洞察：归一化分母可以随时"重基准"。维护一个二元组：

MD = (m, d)：m = 目前见过的最大值；d = 以 m 为基准的指数和 Σ e^{x - m}

两个 MD 的合并律是算法的心脏：

// common.cuh
struct MD { float m, d; };

__device__ __forceinline__ MD md_merge(MD a, MD b) {
  float m = fmaxf(a.m, b.m);
  return {m, a.d * __expf(a.m - m) + b.d * __expf(b.m - m)};
}

推导（合并时把两个局部和折算到新基准 m）：

d_new = Σ_a e^{x - m} + Σ_b e^{x - m}
      = d_a · e^{m_a - m} + d_b · e^{m_b - m}      ← 旧和 × 换算因子

合并律满足结合律 → 可以像加法一样做树形归约（warp shuffle 直接搬 MD 结构体）→ 一趟扫描即可：

一趟读：每线程流式吃进元素，逐个 md = md_merge(md, {x_i, 1.f})
        （局部 max 变大时，旧的 d 自动乘 e^{旧m-新m} 折算——安全且不回读数据）
warp/block 归约：蝶形 __shfl_xor_sync 交换整个 MD（两条 shuffle：一条搬 m、一条搬 d）
第二趟：读 x 一遍，写出 y_i = e^{x_i - m} / d
─────────
全局内存读取 3 次 → **2 次**（读入合并成一趟），写出一次不变

完整 kernel（一个 warp 处理一行，行长 n ≤ 1024，attention score 的典型形态）：

__global__ void softmax_warp_row(const float* __restrict__ x, float* __restrict__ y, int rows, int n) {
  int row = blockIdx.x * (blockDim.x / 32) + threadIdx.x / 32, lane = threadIdx.x % 32;
  if (row >= rows) return;                          // 注意：按 warp 整体判断 row
  const float* xr = x + (size_t)row * n;
  MD md{-FLT_MAX, 0.f};
  for (int i = lane; i < n; i += 32)               // 第 1 趟：流式读 + 逐元素合并
    md = md_merge(md, {xr[i], 1.f});
  #pragma unroll
  for (int o = 16; o > 0; o >>= 1) {               // warp 内蝶形归约整个 MD
    MD other{__shfl_xor_sync(0xffffffff, md.m, o), //   m 走一条 shuffle
             __shfl_xor_sync(0xffffffff, md.d, o)};//   d 走另一条 shuffle
    md = md_merge(md, other);
  }                                                // 32 个 lane 全持 (m, d) ✔
  float inv = 1.f / md.d;                          // 除法变乘法（除法 ~20 周期）
  for (int i = lane; i < n; i += 32)               // 第 2 趟：写出
    y[(size_t)row * n + i] = __expf(xr[i] - md.m) * inv;
}

代码里的门道逐条拆：

  • md = md_merge(md, {x, 1})：单个元素视为 MD{x, 1}（基准是自己、指数和为 e^0=1）——把"逐元素处理"统一成"二元组合并"，流式与归约共用同一算子；
  • MD 过 shuffle：结构体没有对应指令，拆成 m、d 两条 shuffle（换 MD 的打包方式无妨，结合律保证正确）；
  • inv = 1/d 提出循环：n 次除法 → 1 次除法 + n 次乘法；
  • 初始 m = -FLT_MAX、d = 0：空集的单位元（m_merge 的最小元 + d 的加法零元）。

4.4 三个必须亲手测的数值边界（学习目标 ③ 的实践侧）

场景陷阱处理
行内极大值（如 1000）朴素版 e^1000 = Infsafe/online softmax 天然免疫（指数恒 ≤ 0）
mask 填 -INFINITY 的行-inf - (-inf) = NaN 污染整行初始 max 用 -FLT_MAX（有限值），或整行 -inf 单独分支输出全 0
长度为 1 的行 / 空 block除以 d=0？n=1 时 d=e^0=1 正常主要是防御性测试，防止特殊路径漏判

⚠️ mask 语义要分清：注意力 mask 是数据值（-inf 表无效），shuffle 的 mask 是线程位图——两个"mask"重名纯属巧合，面试时混谈是常见扣分点。

4.5 两个来自源页面的性能小抄

  • 累加一律 FP32，即使输入是 BF16/FP16：低精度累加在长行上误差快速放大（BF16 只有 8 位尾数），归约中间量必须升精度；
  • 用 exp2f(x * log2e) 替代 expf：硬件指数指令以 2 为底更快，且缩放系数可合并进外层的一次乘法（FlashAttention 阶段会大量使用此技巧）。

六、原子操作 vs 两趟归约（学习目标 ④）

6.1 大数组归约的最后一公里

到目前为止的归约止步于 block。数亿元素的数组会开几千个 block，各自产出一个部分和——这些跨 block 的部分和怎么合并成最终结果？

方案 A：原子加——最后一个 kernel 一步到位：

if (tid == 0) atomicAdd(result, block_sum);        // 各 block 的 lane 0 抢着累加

方案 B：两趟归约——partial 落盘，第二个 kernel 终归约：

// kernel 1：各 block 部分和写入 partials[blockIdx.x]
if (tid == 0) partials[blockIdx.x] = block_sum;
// kernel 2（第二个 launch）：把几千个 partial 再归约一次

6.2 取舍：三个维度

维度方案 A（atomicAdd）方案 B（两趟归约）
kernel 次数1 次2 次（多一次 launch 开销）
瓶颈格局原子竞争集中在一个地址，block 多时硬件串行化partial 规模小，第二趟成本恒定
确定性顺序不定顺序固定
可复现性每次运行结果可能不同每次严格一致

关键的物理事实：浮点加法不满足结合律（(a+b)+c ≠ a+(b+c)，尾数对齐舍入所致）。原子加的抵达顺序由硬件竞争决定，跑两次可能差在最后几个 ulp——单看是噪声，但它会沿着训练/推理的计算图传播放大。

工程决策规则：

  • 能容忍微小抖动、追求最少改动 → 原子（统计聚合、日志、监控类指标）；
  • 需要可复现（测试对拍、算法评审、论文实验、多卡一致性校验、CI 回归）→ 两趟归约，顺序固定 → 结果逐位一致；
  • 混合策略也常见：kernel 内部树形（确定），跨 block 最后一层才原子（微小不确定性集中在一个 ulp 级别）。

九、练习建议

  1. divergence 可视化（1 小时）：写取模配对与相邻配对两个树形版本，用 Nsight Compute 的 Warp State（Branch / stall 分布）对比分歧计数，再肉眼对比带宽——给教程（一）的 SIMT 理论补上实测证据。
  2. shuffle 语义实验（1 小时）：写一个 kernel，把 __shfl_xor_sync 的 offset 从 16 扫到 1，每步打印各 lane 收到的值（对照 3.1 节手推的表）；再故意在 shuffle 前对部分 lane return，用 compute-sanitizer --tool synccheck 捕捉未定义行为，然后修复它。
  3. 实现 block 版 softmax（2 小时）：按 4.3 节 warp 版改写"一个 block 处理一行"的版本（长行 128K），注意两次 block_reduce（max 与 sum，或一次 MD 归约）之间的 smem 复用屏障——正是源页面警告的陷阱。
  4. 数值边界测试集（1 小时）：构造含 [1000, 1000+1, ...]、整行 -inf、n=1 的测试向量，验证三版 softmax 全部不产生 NaN/Inf；把整行 -inf 的行为对齐 torch.softmax（全 0）。
