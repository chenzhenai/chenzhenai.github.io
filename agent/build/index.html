从 0 到 1 构建 AI Agent
动手编程实践路线

以 Agent 概念为主线，跟随《深入理解 AI Agent：设计原理与工程实践》十章内容，用一个持续演进的项目 mini-agent，从最小的 ReAct 循环一路做到可评估、可进化、可协作的生产级 Agent。

16 个阶段 + 1 个结业项目 · 每个阶段都包含：学习目标、需实现的功能、实践要点、验证方式、阶段性产出。

Agent = LLM + 上下文 + 工具实现层公式 · 全书结构骨架
Agent = Model + Harness生产形态下的展开
Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正“能做事” + “不做错事”

i. 如何使用本教程

本书作者给读者的建议是：不要只读正文，也不必逐行读配套代码，而是读懂设计原则后，借助 Coding Agent（Claude Code、Codex、Cursor 等）从头实现一遍，人负责最初的设计和最终的验收。本教程按这个思路组织：

模块作用怎么用
🎯 学习目标本阶段要弄懂的概念与设计原则先读对应章节，能用自己的话复述这些要点再动手
🛠 需实现的功能本阶段要往 mini-agent 里加的能力可以把它当作给 Coding Agent 的需求说明（Spec）
💡 实践要点书中强调的设计约束与易错点写进你给 Coding Agent 的提示里，或作为代码审查清单
✅ 验证方式可执行的验收标准逐条验证后勾选，进度保存在浏览器本地（左侧进度条）
📦 阶段性产出本阶段结束时应留下的代码、数据与报告每阶段打一个 git tag，便于回溯和对比
📚 参考实验书中对应的配套实验自己实现之后再对照，看差异在哪里、为什么
前置约定（可按需替换）：Python 3.11+；任意 OpenAI 兼容接口、支持工具调用和思考的模型（Kimi、GLM、DeepSeek、Qwen、GPT、Claude 等均可，第 1 章强调绝大多数 Agent 需要支持思考的模型）；会用 Git、命令行、JSON 和 REST API。除第 14 阶段（后训练，需要 GPU）外，其余阶段用 CPU 加 API 即可完成。
关于数据与阈值：文中引用的实验数字均来自书中或配套实验的记录；验收里给出的阈值（如“≥ 80%”）是建议的起点，请按你的模型和任务调整。书中多个实验如实报告了负结果，提醒我们：任何“更好”的结论都要经过自己的评估确认。

环境与地基：接入模型，记录轨迹

在写第一个循环之前，先把“调用模型”和“记录发生了什么”这两件事做扎实。

书：引言 · 第 1 章“如何选择模型”· 第 2 章“消息的四种角色”难度 ★参考用时 0.5 天
本阶段的位置：后面每个阶段都要调用模型、读轨迹、比较指标。地基打得好，后面的评估（阶段 12）和进化（阶段 13）可以直接复用这些轨迹。

🎯学习目标

  • 理解 Chat Completions 的四种消息角色：system、user、assistant、tool
  • 知道选模型要看什么：是否支持思考、工具调用是否稳定、输出速度、多模态能力、策略边界
  • 建立“轨迹就是数据”的意识：轨迹以后会用于调试、评估、经验提炼和训练

🛠需实现的功能

  • agent/llm.py：统一的模型调用入口，base_url、api_key、model 从 .env 读取
  • agent/trace.py：JSONL 轨迹记录器，记录每次请求的消息、响应、token 用量和延迟
  • hello.py：单轮问答，打印回复、token 用量和延迟

💡实践要点

  • 使用标准的结构化消息，不要自己拼接 "USER: … ASSISTANT: …" 字符串：偏离模型训练时的 Chat Template 会削弱多步思考能力
  • 从第一天起记录 usage：阶段 3 的缓存分析和阶段 12 的成本分析都依赖它
  • 轨迹用不绑定任何厂商的中立格式保存（工具调用只记名称和参数），为阶段 9 的跨厂商接管做准备
  • 密钥只放在 .env 里，并加入 .gitignore

✅验证方式

  • python hello.py 返回回复，并打印 prompt/completion token 数与延迟
  • 只改 .env 就能切换到另一家模型厂商，无需改代码
  • traces/*.jsonl 中每行都是合法 JSON，并包含时间戳、用量和延迟

  • 仓库骨架、pyproject.toml、.env.example、agent/llm.py、agent/trace.py；git tag v0.0

# agent/llm.py —— 统一的模型调用入口（OpenAI 兼容协议）
import os, time
from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()
client = OpenAI(base_url=os.getenv("LLM_BASE_URL"), api_key=os.getenv("LLM_API_KEY"))
MODEL = os.getenv("LLM_MODEL")

def chat(messages, tools=None, trace=None, **kw):
    extra = {"tools": tools} if tools else {}
    t0 = time.perf_counter()
    resp = client.chat.completions.create(model=MODEL, messages=messages, **extra, **kw)
    if trace:
        trace.log("llm_call", latency=round(time.perf_counter() - t0, 3),
                  usage=resp.usage.model_dump() if resp.usage else None,
                  n_messages=len(messages))
    return resp

# agent/trace.py —— 只追加的 JSONL 轨迹
import json, time

class Trace:
    def __init__(self, path):
        self.f = open(path, "a", encoding="utf-8")

    def log(self, kind, **data):
        rec = {"ts": time.time(), "kind": kind, **data}
        self.f.write(json.dumps(rec, ensure_ascii=False, default=str) + "\n")
        self.f.flush()

最小 ReAct 循环：Agent = LLM + 上下文 + 工具

一个 while 循环加一个判断：模型返回工具调用就执行并继续，没有就输出结果并退出。

书：第 1 章“ReAct 循环” · 第 2 章“用代码实现 Agent 的核心循环”难度 ★参考用时 1 天产出 v0.1
承上启下：用阶段 0 的 chat() 和 Trace 搭出最核心的 Agent 循环。之后所有的上下文工程，本质上都是在优化这个循环里的 messages 列表。

🎯学习目标

  • 三层理解同一个 Agent：实现层（LLM + 上下文 + 工具）、直觉层（大脑 + 眼睛 + 手脚）、学术层（策略 + 观察空间 + 动作空间）
  • 上下文 = 静态前缀（系统提示词 + 工具定义）+ 轨迹（用户消息 + 模型回复 + 工具结果）
  • “思考 → 行动 → 观察”的循环，以及停止条件：无工具调用、达到最大轮数、遇到不可恢复的错误
  • 并行工具调用：彼此独立的子问题可以在一次输出中同时发出

🛠需实现的功能

  • ToolRegistry：用装饰器注册工具，生成 JSON Schema，按名称分发执行
  • run_agent(task)：ReAct 主循环，带 max_iters 上限
  • 两个工具：convert_currency（固定汇率表）和 calculate（用 ast 实现的安全四则运算，不要用 eval）
  • CLI：python -m agent "你的问题"，每轮打印思考、工具调用和工具结果

💡实践要点

  • assistant 消息要原样追加（包括 tool_calls）；每个 tool_call 都必须有一条 tool_call_id 对应的 tool 消息，否则下一次请求会报错
  • 工具结果统一序列化为 JSON 字符串；工具异常也要返回结果，不能让循环崩溃
  • 部分厂商会返回 reasoning_content 等私有字段，是否需要回传要看厂商文档
  • 保持简单：先不用任何框架，直接调用 API（Anthropic 三原则之一）

✅验证方式

  • 书中的多币种任务（Q1 2.5M 美元、Q2 2.1M 欧元、Q3 1.8M 英镑、Q4 380M 日元，求年度总收入和季度平均）在 4 轮以内得到正确结果（按你的汇率表手算核对）
  • 在轨迹里看到模型在同一次响应中并行发出多个 convert_currency 调用
  • 消融实验 A：去掉系统提示词，记录行为变化
  • 消融实验 B：工具结果改为不回传或返回空字符串，观察重复调用或死循环，并确认 max_iters 能终止它

参考骨架：工具注册表与主循环
import json
from agent.llm import chat

class ToolRegistry:
    def __init__(self):
        self._tools = {}

    def register(self, name, description, parameters, risk="low"):
        def deco(fn):
            self._tools[name] = {"fn": fn, "risk": risk, "parameters": parameters,
                "schema": {"type": "function", "function": {
                    "name": name, "description": description, "parameters": parameters}}}
            return fn
        return deco

    def schemas(self):
        return [t["schema"] for t in self._tools.values()]

    def execute(self, name, arguments):
        if name not in self._tools:
            return json.dumps({"error": "unknown_tool", "available": list(self._tools)})
        try:
            result = self._tools[name]["fn"](**json.loads(arguments or "{}"))
            return json.dumps(result, ensure_ascii=False)
        except Exception as e:
            return json.dumps({"error": type(e).__name__, "message": str(e)}, ensure_ascii=False)

def run_agent(task, registry, system_prompt, max_iters=20):
    messages = [{"role": "system", "content": system_prompt},
                {"role": "user", "content": task}]
    for _ in range(max_iters):
        msg = chat(messages, tools=registry.schemas()).choices[0].message
        messages.append(msg.model_dump(exclude_none=True))
        if not msg.tool_calls:                       # 没有工具调用 → 最终回答
            return msg.content
        for call in msg.tool_calls:                  # 每个调用都必须回传一条 tool 消息
            result = registry.execute(call.function.name, call.function.arguments)
            messages.append({"role": "tool", "tool_call_id": call.id, "content": result})
    return "[stopped] 达到最大迭代次数"

Harness 骨架：约束、验证、纠正

能跑的 Demo 和可靠的产品之间，差的是模型之外、Agent 边界之内的那层运行与治理代码。

书：第 1 章“Harness 工程”“编排模式”“护栏与安全性” · 第 5 章“故障与错误恢复”难度 ★★参考用时 1–2 天产出 v0.2
承上启下：阶段 1 的消融实验已经暴露了脆弱点：幻觉调用、参数错误、重复调用、死循环。本阶段把“约束、验证、纠正”加进循环，让 Agent 从“能做事”走向“不做错事”。

🎯学习目标

  • Agent = Model + Harness；Harness 五要素各自的职责与核心原则
  • 工作流（路径预先写死）与自主 Agent（路径由环境反馈决定）的取舍；“Less structure, more intelligence”：程序只固化必须始终成立的边界
  • 三层护栏：上下文层、执行层、数据层，按“被绕过的难度”排列
  • 故障四层分类：API 层、工具层、上下文层、控制流层

🛠需实现的功能

  1. 参数校验：用 jsonschema 校验参数，失败时返回附带 schema 提示的结构化错误
  2. 幻觉调用处理：调用不存在的工具时返回 unknown_tool 和可用工具列表
  3. 风险分级：工具标注 low / medium / high；high 默认需要人工确认
  4. API 重试：只重试 429、5xx、超时这类可重试错误，指数退避并加随机抖动
  5. 重复调用指纹：对“工具名 + 参数”做哈希计数，超过阈值就提示模型换策略
  6. 熔断与预算：连续失败达到阈值就停止并交给人；限制最大轮数和会话 token 预算
  7. 编排对照：同一个任务分别写一个固定节点的工作流版本和一个自主版本

💡实践要点

  • 工具层错误不终止会话，而是变成模型的输入：错误越具体，模型自我纠正的成功率越高
  • 先判断“值不值得重试”：参数不合法、权限不足这类错误原样重试多少次都一样
  • 安全检查只看结构化字段（工具参数、返回的 JSON），不看模型生成的自由文本，因为后者可能已被注入操纵
  • 故障安全默认值：新工具默认需要授权，显式开放后才自动执行
  • 确认无法恢复之前，不向用户暴露中间错误

✅验证方式

def err(code, message, **extra):
    return json.dumps({"ok": False, "error": code, "message": message, **extra}, ensure_ascii=False)

class Harness:
    def __init__(self, registry, confirm, max_repeat=3):
        self.registry, self.confirm, self.max_repeat = registry, confirm, max_repeat
        self.seen = collections.Counter()

    def run_tool(self, name, raw_args):
        tool = self.registry.get(name)
        if tool is None:                                            # 幻觉调用
            return err("unknown_tool", f"没有名为 {name} 的工具", available=self.registry.names())
        try:
            args = json.loads(raw_args or "{}")
            jsonschema.validate(args, tool["parameters"])            # 验证：参数校验
        except (json.JSONDecodeError, jsonschema.ValidationError) as e:
            return err("invalid_arguments", str(e)[:300], schema=tool["parameters"])
        fp = hashlib.sha256(f"{name}:{json.dumps(args, sort_keys=True)}".encode()).hexdigest()
        self.seen[fp] += 1
        if self.seen[fp] > self.max_repeat:                         # 控制流：无进展循环
            return err("repeated_call", "相同调用已多次执行且无进展，请换一种策略")
        if tool["risk"] == "high" and not self.confirm(name, args): # 约束：人工确认
            return err("denied", "用户拒绝了该操作")
        try:
            return json.dumps({"ok": True, "result": tool["fn"](**args)}, ensure_ascii=False)
        except Exception as e:                                      # 纠正：错误交还给模型
            return err(type(e).__name__, str(e)[:500])

def with_retry(fn, *args, retries=4, base=1.0, **kw):
    for attempt in range(retries + 1):
        try:
            return fn(*args, **kw)
        except RETRYABLE:
            if attempt == retries:
                raise
            time.sleep(base * 2 ** attempt + random.uniform(0, base))   # 指数退避 + 抖动

上下文工程 III：压缩、隔离与提示注入防御

为上下文做减法，并守住“数据不是指令”的边界。

承上启下：前两个阶段都在往上下文里加内容。随着任务变长，上下文会膨胀、腐化，外部内容还可能夹带恶意指令。本阶段处理“减法”和“安全”，之后 Agent 才能承担长任务。

🎯学习目标

  • 压缩的三个动机：长度与成本约束、提升思考质量（把需要推导的结论变成可以直接检索的知识）、缓解上下文焦虑
  • 上下文腐化与上下文溢出的区别：腐化是“装得下但找不到”
  • 压缩和 KV Cache 的权衡：在两次调用之间、接近阈值时批量压缩
  • 隔离优于压缩：让大体积的中间信息根本不进入主上下文
  • 提示注入和越狱的区别；上下文层防御的结构性上限

🛠需实现的功能

  • 工具结果预算：超长的工具输出存到磁盘，上下文里只放预览和文件路径
  • 自适应窗口压缩：prompt token 超过窗口的 80% 时，一次性压缩所有未压缩的工具结果，并打上 [COMPRESSED] 标记防止重复压缩
  • 上下文感知压缩：压缩提示里带上当前查询和已有信息，摘要中保留来源 URL
  • 压缩熔断：压缩连续失败 3 次就停止尝试
  • 注入防御：外部内容加来源标签包裹；系统提示词声明标签内是数据而不是指令；高风险动作走执行层审批
  • 注入对照矩阵：3 种攻击（网页隐藏指令、文档里的“忽略之前的指令”、工具结果中伪造的用户消息）× 4 种防御配置

💡实践要点

  • 压缩时保留四类信息：决策、约束、失败路径、引用来源；“Sutskever 于 2024 年 5 月离开 OpenAI”不能压成“Sutskever 离开”
  • 不要每轮都压缩，否则会频繁破坏缓存
  • 让 Agent 定期把进展写进文档，而不是只留在执行历史里
  • 处在同一个上下文里的 Agent 很难判断自己是否已被注入，所以上下文层只能降低攻击成功率，兜底要靠执行层和数据层

✅验证方式

  • 设计一个需要 7 次以上大体积搜索的调研任务，人为把窗口限制在 32K：不压缩时溢出失败，压缩后可以完成

  • 已压缩的内容不会被再次压缩（检查 [COMPRESSED] 标记）
  • 完成注入矩阵：每格至少 5 次，记录攻击成功率，确认防御叠加后成功率下降

import math
from collections import Counter, defaultdict

def bm25_scores(query_terms, docs, k1=1.5, b=0.75):
    """docs: 分词后的文档列表（每个元素是 token 列表）"""
    N = len(docs)
    avgdl = sum(len(d) for d in docs) / N
    df = Counter(t for d in docs for t in set(d))
    scores = []
    for d in docs:
        tf, s = Counter(d), 0.0
        for t in query_terms:
            if t in tf:
                idf = math.log(1 + (N - df[t] + 0.5) / (df[t] + 0.5))
                s += idf * tf[t] * (k1 + 1) / (tf[t] + k1 * (1 - b + b * len(d) / avgdl))
        scores.append(s)
    return scores

def rrf(rankings, k=60):
    """rankings: 多路检索各自排好序的 doc_id 列表"""
    fused = defaultdict(float)
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking, start=1):
            fused[doc_id] += 1 / (k + rank)
    return sorted(fused, key=fused.get, reverse=True)

from pathlib import Path

def run_python(code: str, timeout: int = 20) -> dict:
    with tempfile.TemporaryDirectory() as d:
        script = Path(d, "main.py")
        script.write_text(code, encoding="utf-8")
        try:
            p = subprocess.run([sys.executable, "-I", str(script)], cwd=d,
                               capture_output=True, text=True, timeout=timeout)

            return {"ok": False, "error": f"执行超时（超过 {timeout} 秒）"}
        return {"ok": p.returncode == 0,
                "stdout": truncate_output(p.stdout), "stderr": truncate_output(p.stderr)}

import asyncio

async def event_loop(agent, queue: asyncio.Queue):
    pending = []
    while True:
        if not pending and not agent.has_unanswered_tool_results():
            pending.append(await queue.get())               # 空闲：等待事件唤醒
        agent.append_events(pending)                        # 安全点：批量注入事件
        pending = []
        turn = asyncio.create_task(agent.step())            # 一步 = 一次推理 + 其工具执行
        while not turn.done():
            getter = asyncio.create_task(queue.get())
            done, _ = await asyncio.wait({turn, getter}, return_when=asyncio.FIRST_COMPLETED)
            if getter not in done:                          # 本步正常结束
                getter.cancel()
                break
            ev = getter.result()
            if ev["urgency"] == "urgent":                   # 取消式：主动制造安全点
                turn.cancel()
                await asyncio.gather(turn, return_exceptions=True)
                agent.close_dangling_tool_calls("[cancelled] 被打断，未执行完成")
                pending.append(ev)
                break
            if ev["urgency"] == "parallel":                 # 并行式：另起会话，不打断主任务
                asyncio.create_task(agent.side_query(ev))
            else:                                           # 队列式：等本步结束后注入
                pending.append(ev)

from math import comb

def pass_at_k(n, c, k):
    """n 次运行中 c 次成功；至少一次成功的概率（无偏估计）"""
    return 1.0 if n - c < k else 1 - comb(n - c, k) / comb(n, k)

def pass_hat_k(n, c, k):
    """Pass^k：随机抽取 k 次运行全部成功的概率"""
    return comb(c, k) / comb(n, k)

def release_gate(candidate, baseline, boundary_set, retention_set, min_gain):
    gain = score(candidate, boundary_set) - score(baseline, boundary_set)   # 应当改变的样本
    regressions = [t for t in retention_set                                  # 不应受影响的样本
                   if passed(baseline, t) and not passed(candidate, t)]
    return gain >= min_gain and not regressions

工具静默修改参数模型看到的世界和实际不一致，陷入无法自诊断的失败参数传递保持透明（8）
写完代码就宣布完成没有经过验证的“完成”测试通过才算完成（9）
一开始就搭复杂工作流或多 Agent拓扑僵化，越补越复杂，通用性越来越差从简单开始，只在评估反复暴露稳定失败时才增加结构（1、15）
把反思当作证据错误的经验被固化只采纳有环境结果和多条轨迹支持的经验（13）
只看 Pass@k高估业务可用性同时报告 Pass^k（12）
